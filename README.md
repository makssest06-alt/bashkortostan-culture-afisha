# Афиша культуры Башкортостана

Командный репозиторий хакатона «Кибер 102», задача 1 «Афиша культуры Башкортостана». Официальное ТЗ: [`docs/TZ.pdf`](docs/TZ.pdf).

Делаем информационный сервис о культурных событиях республики: концерты, спектакли, выставки, фестивали, кино, экскурсии. Один каталог и один REST API обслуживают Telegram-бота, сайт, встраиваемый виджет и ИИ-агента. Министерство может забрать данные через открытый API и встроить виджет к себе, не меняя свои системы.

> Это **неофициальный** сервис команды хакатона. Он не является сервисом Министерства культуры Республики Башкортостан, и интерфейс должен говорить об этом явно (ТЗ, п. 13, «красные линии»).

## Уровень решения

**Выбран уровень 3 «Агент» (85 баллов).**

- Уровни кумулятивные: уровень 3 = бот (ур. 1) + сайт, API, виджет, админка, дедупликация (ур. 2) + ИИ-агент в боте и на сайте.
- Уровень 4 добавляет сбор из внешних источников, планировщик «Выходной день», 60 контрольных запросов с отчётом. Для 48 часов это большой риск.
- Оценка = баллы уровня × коэффициент качества. Аккуратный уровень 2 может обойти уровень 3 с проваленными метриками (п. 5). Поэтому запасной план — сдать уровень 2 и включить агента, только если его метрики проходят пороги п. 9.2.

На защите показываем уровень 3 в режиме `rules-v2`. Подключаемая внешняя модель и гибридный режим доступны в конфигурации сервера. Независимая проверка по п. 9.2 ожидает внешние запросы проверяющих.

## Запуск

### Целевой запуск: одна команда

По ТЗ (п. 10) сервис поднимается так, на чистой машине, не дольше 10 минут:

```bash
./scripts/bootstrap-env.sh   # создаст .env и сгенерирует ADMIN_TOKEN/POSTGRES_PASSWORD
# затем впишите TELEGRAM_BOT_TOKEN (и LLM_API_KEY, если нужен живой LLM)
docker compose up --build
```

Корневой [`docker-compose.yml`](docker-compose.yml) поднимает `postgres` (`postgres:16-alpine` с healthcheck и томом `afisha-postgres-data`), `api` (`backend/`, внутренний порт `8000`, наружу опубликован только на `127.0.0.1:${API_PORT:-8000}`, healthcheck `/api/v1/health`), `bot` (`bot/`, long polling; нужен `TELEGRAM_BOT_TOKEN`) и `web` через `include: [web/compose.yaml]` на `http://localhost:3210` (по умолчанию `NEXT_PUBLIC_API_BASE_URL=http://api:8000`).

## Как подключить бэк к сайту

Код сайта менять не нужно: адрес бэка задаётся переменной `NEXT_PUBLIC_API_BASE_URL`.

| Значение | Что делает сайт |
|---|---|
| пусто (по умолчанию) | работает на своих моках из `web/src/app/api/v1`, бэк не нужен |
| `http://localhost:8000` | берёт данные из бэка: `http://localhost:8000/api/v1/...` |

- Адрес пишется без `/api/v1` на конце. Если префикс всё же указан, сайт его срежет.
- Опечатка в адресе (нет `http://`, есть логин или параметры) роняет `npm run build` с понятной ошибкой. Сайт не переключается молча обратно на моки.
- Переменная с приставкой `NEXT_PUBLIC_` вшивается при сборке. После смены адреса сайт нужно собрать заново: `npm run build`, а в Docker — `docker compose up --build`.

### Как переключить сайт с моков на бэк

Локально, бэк запущен на этой же машине:

```bash
cd web
echo 'NEXT_PUBLIC_API_BASE_URL=http://localhost:8000' >> .env.local
echo 'ADMIN_TOKEN=<токен модератора, тот же, что у бэка>' >> .env.local
npm run dev            # или npm run build && npm start
```

В Docker, бэк на этой же машине:

```bash
cd web
NEXT_PUBLIC_API_BASE_URL=http://host.docker.internal:8000 ADMIN_TOKEN=<токен> docker compose up --build
```

В общем `docker-compose.yml` рядом с бэком (когда он появится):

```yaml
include:
  - web/compose.yaml
```

и в `.env` рядом с ним: `NEXT_PUBLIC_API_BASE_URL=http://api:8000`, где `api` — имя сервиса бэка. Снаружи бэк можно не открывать: к нему ходит только сервер сайта.

Проверить, что сайт видит бэк:

```bash
curl -i http://localhost:3210/api/v1/health        # ответ бэка, пересланный сайтом
curl -s 'http://localhost:3210/api/v1/events?page_size=1'
```

### Как это устроено

- **Страницы** (каталог, карточка, `/ask`, `/embed`, `/developers`) сервер сайта запрашивает у бэка напрямую. Тайм-аут 8 секунд, у ассистента 20 секунд. Если бэк не ответил, страница показывает «Не загрузилось… Повторить», а не пустую выдачу.
- **Браузер, виджет на чужих сайтах и примеры curl** ходят только на `/api/v1/*` самого сайта, а сайт пересылает запрос в бэк. Поэтому бэку не нужен CORS. Сайт передаёт в бэк адрес посетителя (`X-Forwarded-For`) для лимитов частоты, `If-None-Match`/`If-Match` и `X-Request-Id`. Cookie сайта в бэк не уходит.
- **Админка** `/admin`: вход проверяет сам сайт по своему `ADMIN_TOKEN`, а запросы к `/api/v1/admin/*` пересылает в бэк с заголовком `Authorization: Bearer <ADMIN_TOKEN>`. Токен в браузер не попадает, у сайта и бэка он должен совпадать. `/api/v1/admin/session` (вход и выход) в бэк не пересылается.
- **Бэк недоступен** — сайт отвечает `503 unavailable` в формате ошибок контракта.
- Если сайт стоит за nginx, nginx должен выставлять `X-Forwarded-For`: сайт передаёт бэку то, что получил.

Код: `web/src/lib/api/config.ts` (адрес), `web/src/lib/api/forward.ts` (пересылка), `web/src/lib/admin/forward.ts` (админка), `web/src/lib/api/wire.ts` и `wire-list.ts` (разбор ответов бэка).

### Какие методы из `contracts/api.openapi.yaml` нужны сайту

Без этих методов соответствующая часть сайта не работает.

| Метод | Где на сайте | Что важно |
|---|---|---|
| `GET /events` | каталог, главная, виджет и `/embed`, резервный поиск `/ask`, блок «Ещё в Уфе» в карточке | Фильтры `city`, `category`, `date`, `date_from`, `date_to`, `time_from`, `time_to`, `price_max`, `free=true`, `age`, `q`, `sort`, `page`, `page_size`. Только `status = published` |
| `GET /events/{id}` | карточка `/events/{id}` | Отменённое событие отдаётся (сайт показывает «Отменено»), черновик — 404. `ETag` и 304 на `If-None-Match` |
| `POST /feedback` | форма заявки на `/about` и в карточке | 202 `{ id, status }`. Ошибки полей — в `details[].field`: сайт подсвечивает поле. 429 с `Retry-After` |
| `GET /health` | проверка после выкладки | Сайт пересылает как есть |
| `GET/PATCH /admin/events`, `/admin/events/{id}` | админка: список, правка, статусы | `PATCH` с `If-Match`: без него 409, устарел — 412 |
| `POST/GET /admin/imports` | админка: импорт CSV/JSON и история | Отчёт `ImportReport` |
| `GET /admin/moderation`, `POST /admin/moderation/{id}/resolve` | админка: очередь спорных | Решения `publish`, `keep_draft`, `cancel`, `merge` |
| `GET /admin/audit` | админка: журнал изменений | — |

Остальные методы контракта (`/cities`, `/venues`, `/categories`, `/venues/{id}/schedule`, `/events/{id}/similar`, `/subscriptions`) сайт сам не вызывает, но пересылает их в бэк для виджета и сторонних сайтов. `/metrics` и неизвестные пути `/admin/*` наружу через сайт не открываются.

Каталог отправляет ещё три параметра вне контракта: `age_rating` (метки 0+…18+), `audience=kids` (раздел «Детям») и `status`. Бэк, сделанный строго по контракту, их не знает: если он их пропустит, выдача придёт без этих условий. Чтобы фильтры «Возраст» и «Детям» работали с бэком, их нужно внести в контракт или в бэк.

**Обязательной части контракта сайту хватает.** Бэк может отдавать событие только с полями п. 8.1, а список — только с `items`, `page`, `page_size`, `total`, `total_pages`. Тогда сайт сам соберёт сеанс из `date_start`/`date_end`, тарифы из `price_min`/`price_max`, источник из `source_url`, код города по названию из `city`. Фильтры покажутся без чисел.

Необязательные расширения контракта делают сайт полнее:

| Расширение | Что даёт на сайте |
|---|---|
| `occurrences` | Несколько сеансов, перенос, «билеты кончились» |
| `sources` | Все источники в блоке «Источники» после дедупликации |
| `offers` | Тарифы: взрослый, детский, льготный |
| `city_id`, `venue_id` | Точные коды города и площадки |
| `image`, `popularity`, `organizer`, `title_ba` | Картинка, сортировка по популярности, организатор, название по-башкирски |
| `facets` в ответе `GET /events` | Числа у фильтров. Подходит и форма контракта (`age_limits`, подписи строкой), и форма сайта |
| `relaxations` с полем `query` | Кнопки «ослабить условия» при пустой выдаче. Вариант без готового `query` сайт не показывает |

Методы вне контракта v1. Бэк может их не делать, у сайта для каждого есть запасной путь:

| Метод | Зачем сайту | Если бэк его не отдаёт / детали |
|---|---|---|
| `POST /assistant/query`, `POST /assistant/confirm` | ИИ-подбор `/ask` и одноразовое подтверждение действий | Бэк реализует оба метода; при 503 `/ask` переключается на обычный поиск с теми же фильтрами (п. 7.5) |
| `GET /dictionaries` | Подписи городов, категорий и статусов на двух языках | Реализован в бэке; при отсутствии берутся справочники сайта |
| `GET /facets` | Числа на главной | Реализован в бэке; запасной путь — `facets` списка |
| `GET/PATCH /admin/applications`, `GET /admin/traces` | Вкладки «Обращения» и «Трассы ИИ» в `/admin` | Оба маршрута реализованы в бэке и проксируются сайтом |
| `POST /admin/reset` | Сброс демо-данных | Реализован в бэке для демо-стенда |

Полный список с пояснениями: [`web/.env.example`](web/.env.example). Реальные токены в репозиторий не кладутся (`.env`, `.env.local` в `.gitignore`).

| `ASSISTANT_DISABLED` | при запуске | `1` выключает ИИ-подбор: `/ask` показывает обычный поиск. Работает и с бэком |

## Модель и стоимость диалога

- **Модель и промпт (`PROMPT_VERSION = afisha-agent-v2`)**: `gpt-4o-mini` через OpenAI-совместимый endpoint (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`), до 5 вызовов инструментов на ответ (`MAX_TOOL_CALLS_PER_ANSWER = 5`, `contracts/agent_tools.json`), память последних 5+ реплик (`history` + накопленные ограничения `previous`), фильтрация `grounding_ids` для исключения выдуманных событий и изоляция недоверенного текста карточек тегом `<untrusted_event_data>` с очисткой `<`/`>`.
- **Расчёт стоимости диалога**: `0.015 ₽ / 1K prompt tokens + 0.06 ₽ / 1K completion tokens` (переопределяется через `LLM_COST_IN_RUB_PER_1K` / `LLM_COST_OUT_RUB_PER_1K`, хранится в `agent_traces.cost_rub`). Один ответ обходится в ~0,04–0,12 ₽, диалог на 5 реплик — ~0,25–0,60 ₽ (существенно ниже порога ТЗ п. 9.2 ≤ 5 ₽).
- **Режимы без внешнего LLM (`rules-v2` и `rules-fallback-v2`)**: при пустом `LLM_API_KEY` работает детерминированный ИИ-пайплайн `rules-v2` (стоимость `0.00 ₽`); при ошибке/таймауте внешнего провайдера (`LLM_TIMEOUT_MS`) ассистент автоматически переходит на `rules-fallback-v2` (ошибка LLM пишется в трассу, а не роняет ответ). При `ASSISTANT_DISABLED=1` или `X-Assistant-Demo: unavailable` возвращается `503` + `Retry-After: 60`, а `/ask` и Telegram-бот автоматически переходят на обычный поиск.
- **Лимиты и бюджет (P0-3)**: `/assistant/query` ограничен по `user_ref` (`ASSISTANT_RATE_LIMIT_10M=20` за 10 минут, `ASSISTANT_DAILY_LIMIT=200` за сутки) и высоким IP-backstop (500/10 мин), чтобы пользователи бота/сайта за общим прокси не блокировали друг друга; `/assistant/confirm` — отдельно (`ASSISTANT_CONFIRM_LIMIT_10M=20`), ответ — `429` + `Retry-After`. Ответ модели ограничен `ASSISTANT_MAX_TOKENS=800`. Дневной бюджет `ASSISTANT_DAILY_BUDGET_RUB=100` считается по `agent_traces.cost_rub`: при исчерпании LLM не вызывается, ассистент отвечает `rules-budget-v2`, в трассу пишется `daily_budget_exhausted`, растут метрики `afisha_rate_limited_total` и `afisha_assistant_budget_fallbacks_total`; при 80% бюджета — предупреждение в лог. `/metrics` в production закрыт `METRICS_TOKEN` (без токена — 404).

## Данные и персональные данные

- Выдуманных мероприятий нет. Демо-события в сиде и тестовых фикстурах (`backend/fixtures/*`) синтетические и помечены `synthetic: true`.
- Подписка (`subscriptions`) хранит только непрозрачный идентификатор пользователя `user_ref` (в боте — HMAC от chat_id с серверной солью) и фильтры. `user_ref` передаётся заголовком `Authorization: Bearer <user_ref>` и не принимается в query string, в ответах списка не возвращается. Отписка (`DELETE /api/v1/subscriptions/{id}`) физически удаляет запись (`204`) и без `user_ref` невозможна. Подтверждения ассистента привязаны к `user_ref`, живут 5 минут, хранятся хешем и ограничены отдельным rate-limit. Неактивные подписки подлежат очистке по истечении **180 дней** без активности.
- Обращения обратной связи (`feedback`) хранят имя и контакт только для ответа модератора/организатора, **никогда не пишутся в логи и `audit_log`**, а срок хранения задаётся переменной `FEEDBACK_RETENTION_DAYS=90` (по умолчанию **90 дней**). Трассы агента (`agent_traces`) перед записью автоматически маскируют email и телефоны (`[email]`, `[phone]`).

## Известные ограничения

- Заказчик не предоставил подготовленный набор мероприятий из Приложения В к ТЗ. В чате кейса 13 ноября организаторы подтвердили, что такого набора нет, и предложили использовать открытые источники. На демонстрационном стенде используется синтетический каталог с отметкой `synthetic: true`. Для проверки импорта используется тестовый файл `backend/fixtures/import-100.csv`.
- Башкирские тексты сайта вычитаны без носителя языка. Спорные строки с запасными вариантами: [`docs/BA_REVIEW.md`](docs/BA_REVIEW.md).
- Текущие замеры качества и безопасности получены автоматическим прогоном [`docs/EVAL_REPORT.md`](docs/EVAL_REPORT.md) на встроенном контуре (`rules-v2` + `@electric-sql/pglite`, mock LLM проверяется в автотестах `backend/test/assistant.test.ts`); прогон на внешнем живом LLM-провайдере требует реального `LLM_API_KEY`.
- Запись демо-видео на 5 минут и публикация публичного стенда выполняются перед финальной сдачей.

## Базовые принципы

1. Один каталог и один API для сайта, бота, виджета и агента.
2. У каждого события есть источник, время проверки и статус. Неизвестная цена (`null`) — это не «бесплатно», неизвестный возраст — не «0+».
3. Отменённое событие не попадает в выдачу, но открывается по прямой ссылке с пометкой.
4. Жёсткие фильтры (дата, город, цена, возраст, статус) проверяет детерминированный код. Агент берёт факты только из результатов инструментов.
5. При отключённой модели поиск и карточки работают.
6. Секреты, токены и персональные данные не попадают в репозиторий и логи.
