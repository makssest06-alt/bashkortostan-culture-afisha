# Правила командной работы

Эти правила помогают команде быстро разрабатывать проект без потери изменений и конфликтов. Они действуют со старта подготовки и на протяжении хакатона.

## 1. Организация задач

- Любая работа начинается с Issue: проблема, ожидаемый результат, критерии приёмки, исполнитель.
- Одна задача — один исполнитель. Если нужна помощь, она фиксируется в Issue.
- Для спорных решений сначала короткое обсуждение, затем итог записывается в `docs/DECISIONS.md`.
- Нельзя молча менять чужую задачу, API-контракт или схему данных.

Рекомендуемые метки:

- `priority/high`, `priority/medium`, `priority/low`;
- `area/product`, `area/research`, `area/data`, `area/backend`, `area/frontend`, `area/telegram`, `area/ai`, `area/design`, `area/qa`;
- `blocked`, `needs-review`, `demo`.

## 2. Ветки

Основная ветка — `main`. Прямые коммиты в неё не используются, кроме начальной настройки репозитория.

Формат названий:

```text
feat/12-event-filters
fix/24-date-timezone
docs/8-architecture
research/5-analogues
chore/3-ci-setup
```

Правила:

- ветка создаётся из актуального `main`;
- одна ветка решает одну задачу;
- ветки короткоживущие, желательно не дольше одного рабочего дня;
- перед PR нужно подтянуть изменения из `main` и разрешить конфликты у себя;
- force-push в общие ветки запрещён.

## 3. Коммиты

Используем Conventional Commits:

```text
feat: добавить фильтр событий по городу
fix: учитывать часовой пояс при выборе даты
docs: зафиксировать контракт события
test: проверить дедупликацию одинаковых событий
chore: настроить проверки в CI
```

Коммит должен содержать логически законченное изменение. Не смешиваем форматирование всего проекта с новой функциональностью.

## 4. Pull Request

- PR создаётся как можно раньше; незавершённая работа помечается Draft.
- В описании: что сделано, зачем, как проверить, связанный Issue, ограничения.
- Для интерфейсов прикладываем скриншоты или короткое видео.
- Желательный размер — до 400 изменённых строк без учёта сгенерированных файлов.
- Перед merge нужен минимум один approve от другого участника и успешные автоматические проверки, когда CI будет настроен.
- Ревьюер проверяет не только стиль, но и корректность, безопасность и соответствие критериям задачи.
- Используем Squash and merge, чтобы в `main` оставалась понятная история.
- Ветку после merge удаляем.

Во время хакатона команда старается брать PR в ревью в течение 30 минут. Блокирующие замечания обсуждаем голосом, но итог фиксируем в PR.

## 5. Настройки защиты main

Владельцу репозитория нужно включить в GitHub Settings → Rules → Rulesets:

- запрет прямых push в `main`;
- обязательный pull request;
- минимум одно одобрение;
- обязательное прохождение проверок CI после их появления;
- запрет force-push и удаления ветки;
- автоматическое устаревание approve после новых коммитов.

До включения технической защиты эти требования действуют как командное соглашение.

## 6. Качество и Definition of Done

Задача считается выполненной, когда:

- выполнены критерии приёмки из Issue;
- код или документ прошли ревью;
- добавлены или обновлены уместные тесты;
- локальный запуск и проверки не сломаны;
- обновлены документация и `.env.example`, если изменился запуск;
- нет секретов, мусорных файлов и отладочного вывода;
- демонстрационный сценарий продолжает работать.

## 7. Данные и ИИ

- Не добавляем выдуманные мероприятия в основной каталог даже для демо.
- Для каждого события сохраняем URL источника, дату получения и дату последней проверки.
- Отменённые, перенесённые и прошедшие события не удаляем молча: им присваивается явный статус.
- Дедупликация не должна без подтверждения объединять сомнительные пары.
- ИИ-агент получает события через API или слой запросов к базе, а не придумывает их.
- Фильтры даты, цены, возраста и статуса должны быть детерминированными и проверяемыми.
- Если данных недостаточно, агент задаёт уточняющий вопрос или честно сообщает об ограничении.

## 8. Безопасность

- В Git не попадают `.env`, токены, пароли, приватные ключи и дампы с персональными данными.
- В репозитории хранится только `.env.example` с названиями переменных и безопасными примерами.
- Доступы выдаются по принципу минимальных прав.
- Секреты для CI и развёртывания хранятся в GitHub Secrets или менеджере секретов.
- При случайной публикации секрета его сначала отзывают и перевыпускают, затем очищают историю.

## 9. Коммуникация

- Короткий статус по направлениям: что сделано, что дальше, что блокирует.
- Решения и договорённости не остаются только в мессенджере: итог переносится в Issue, PR или `docs/`.
- Красная сборка `main` — приоритет команды; новые функции временно не начинаем.
- Никто не ломает чужой сценарий ради своего: спорные изменения сначала обсуждаются.
