# Benchmark русскоязычного query understanding

## Что здесь измеряется

`queries.jsonl` содержит **120 запросов** для проверки превращения русскоязычного сообщения в ограничения поиска афиши. Это не набор выдуманных событий и не набор правильных поисковых результатов.

Сейчас можно измерять:

- действие системы: поиск, обязательное уточнение или out-of-scope;
- точность hard/soft-ограничений;
- нормализацию дат относительно зафиксированного `reference_now`;
- различие цены за человека и общего бюджета;
- различие времени начала и интервала, в который событие должно поместиться целиком;
- корректность уточнений;
- сохранение состояния через `SessionPatch`;
- запрет выдумывания событий, цен, ссылок и запрещённых действий.

Здесь **нельзя** честно вычислять Recall@k, nDCG@k, MRR или реальную latency поиска: нет каталога, снапшота данных и qrels с релевантными `occurrence_id`.

## Состав

| Категория | ID | Количество | Основной объект проверки |
|---|---|---:|---|
| `absolute_dates` | ABS | 10 | явные даты, диапазоны, смена года, високосный день |
| `relative_dates` | REL | 10 | завтра, послезавтра, будни и выходные |
| `time_windows` | TIM | 10 | начало события против доступного интервала |
| `budget` | BUD | 10 | за человека, на всех, бесплатно, мягкая цена |
| `participants_age` | AGE | 10 | участники, дети, рейтинг, отсутствующий возраст |
| `categories` | CAT | 10 | обязательные, альтернативные и мягкие категории |
| `semantic_soft` | SEM | 10 | атмосфера, интерактивность и другие предпочтения |
| `geo_venue` | GEO | 10 | города, регион, площадка, неизвестная геолокация |
| `typos_language` | TXT | 10 | опечатки, смешанная раскладка, транслит, названия |
| `ambiguity` | AMB | 10 | противоречия и необходимые уточнения |
| `followups` | FOL | 10 | изменение, снятие и сброс условий |
| `safety_invariants` | SAFE | 10 | статусы, факты и запрещённые действия |

Разметка: 72 `dev`, 48 `test`; 105 `search`, 13 `clarify`, 2 `out_of_scope`. Каждая категория содержит 6 dev и 4 test случая.

`test` здесь — видимый регрессионный набор, а не окончательный скрытый holdout. После настройки нужен новый независимый набор, желательно из реальных диалогов. Текущая разметка подготовлена с LLM-ассистированием и прошла автоматические проверки, но ещё не является независимой двойной человеческой разметкой.

## Запуск проверки

Из корня репозитория:

```bash
python3 evals/search/validate.py
```

Встроенные проверки не требуют зависимостей. Если установлен пакет `jsonschema`, дополнительно выполняется полная проверка по `constraints.schema.json`:

```bash
python3 -m pip install 'jsonschema>=4.23,<5'
python3 evals/search/validate.py
```

Валидатор проверяет 120 уникальных ID и текстов, 12 категорий по 10 примеров, отсутствие пересечения семей между split, диапазоны дат и времени, согласованность участников и бюджета, а также механически применяет все 10 патчей к предыдущему состоянию.

Чтобы измерить поведение агента без LLM, установите зависимости (`npm --prefix backend ci`), затем из корня запустите `node evals/run-evals.mjs`. В `docs/EVAL_REPORT.md` метрика 9.2-4 считается по всем запросам с `expected.action: "clarify"` (13 из 120, включая 10 `AMB-*`). Успех — непустой вопрос без поисковой выдачи. Отчёт отдельно проверяет код первого вопроса по `expected.clarify` и показывает лишние уточнения на остальных запросах.

Для оценки по ТЗ добавьте независимый файл из 10 внешних запросов, которых нет в `queries.jsonl`:

```bash
node evals/run-evals.mjs --external /path/to/external.jsonl
```

Используйте поля `id`, `query`, `reference_now` и `expected` из примера ниже; для `expected.action: "clarify"` укажите допустимые коды первого вопроса в `expected.clarify`. Команда печатает оба замера и берёт худший для проверки порогов 80% и 90%. Если во внешнем наборе нет ожидаемых уточнений, итог по 9.2-4 будет `null`. Внешние запросы и результаты этого режима не записываются в репозиторий.

Для воспроизводимой проверки есть [10 дополнительных запросов из аудита PR](clarification-challenge.jsonl) и [результаты по каждому случаю](../../docs/CLARIFICATION_CHALLENGE.md). Набор для официальной приёмки предоставляют независимые проверяющие.

## Контракт одного случая

```json
{
  "id": "BUD-003",
  "family": "bud-b",
  "category": "budget",
  "split": "dev",
  "query": "На двоих до 2000 в Уфе завтра",
  "reference_now": "2026-11-11T12:00:00+05:00",
  "timezone": "Asia/Yekaterinburg",
  "expected": {
    "action": "search",
    "hard": {
      "cities": ["ufa"],
      "date": {"from": "2026-11-12", "to": "2026-11-12"},
      "participants": {"total": 2},
      "max_total_price": 2000,
      "currency": "RUB"
    },
    "soft": {}
  },
  "retrieval_focus": ["total_budget", "participants"]
}
```

Отсутствующее поле означает **«условие не задано»**. Это не ноль, не пустой список и не разрешение подставить значение по умолчанию. Пустые `hard` и `soft` означают, что ограничений соответствующего типа нет.

### Даты и время

- Все ожидаемые относительные даты уже вычислены от `reference_now`; системные часы во время eval использовать нельзя.
- Таймзона набора — `Asia/Yekaterinburg`, UTC+5.
- `date.from` и `date.to` — включённые локальные календарные даты. Для SQL день лучше представлять полуинтервалом `[начало_дня; начало_следующего_дня)`.
- Диапазон дат также включает обе даты.
- «В субботу» — ближайшая будущая суббота; «в следующую субботу» в этом протоколе — суббота следующей календарной недели. Такая интерпретация должна быть видна пользователю как редактируемое допущение.
- «Вечером» в тестовой политике — 18:00–23:00 для **начала** события. Это настраиваемое допущение, а не языковая истина.
- `start_from <= start_at < start_to` описывает начало.
- `fits_from/fits_to` требует, чтобы начало и конец события целиком помещались в доступный интервал. Если длительность неизвестна, backend не должен выдумывать её.
- В v1 временные окна находятся в пределах одних суток; интервал 23:00–02:00 этой схемой не выражается. Для ночных событий контракт нужно расширить абсолютными datetime/offset либо явным признаком следующих суток, а не сравнивать время «по кругу».
- Прошедшая дата не заменяется незаметно на сегодня или завтра.

### Бюджет

- «Билет до 1000» — `max_price_per_person`.
- «На двоих до 2000», «2000 на всех» — `max_total_price`.
- Если масштаб цены не следует из запроса, базовая политика использует цену за человека и отображает это допущение. Формулировка «на всех» имеет приоритет.
- Неизвестная цена не равна нулю и не проходит строгий ценовой фильтр как уже проверенная цена.
- `free_only=true` требует явного бесплатного входа или нулевой цены из данных.
- «Хотелось бы бесплатно, но не обязательно» — soft-предпочтение, а не скрытый жёсткий фильтр.

### Возраст и участники

- `children_ages` хранит точные возрасты детей; при нескольких детях строгость проверки обычно определяется самым младшим, но окончательное правило зависит от смысла возрастного ограничения в данных.
- «Для взрослых» само по себе не означает, что нужен рейтинг именно `18+`.
- «Без детей» описывает состав группы и не добавляет автоматически `required_age_rating=18+`.
- Если нужно обещать соответствие ребёнку, а возраст неизвестен, система уточняет его.
- Неизвестный возрастной рейтинг события нельзя незаметно считать подходящим.

### Hard, soft и пустой результат

Явные «только», «исключительно», «не дороже», «без кино» — hard. «Хотелось бы», «предпочитаю», «не очень люблю» — soft.

`title_query`, `topic_query`, `venue_query` и `geo_query` в `hard` обозначают обязательный предмет поиска, но не наивный SQL `AND` по сырой строке. Их соответствие оценивается по canonical ID или каноническому смыслу: эквивалентный alias не является ошибкой или ослаблением, а подмена произведения, темы или площадки — является. Даты, деньги, категории, статусы и участники сравниваются детерминированно.

По умолчанию можно автоматически предлагать варианты с ослаблением soft-предпочтений. Hard-ограничения не ослабляются незаметно. Исключение — явно записанное пользователем `allowed_relaxations`, например заранее разрешённый перенос на другой день. Любой вариант ослабления показывается отдельно, с реальным количеством результатов.

### Follow-up

У follow-up есть `previous`, `expected.patch` и итоговые `expected.hard/soft`:

- `reset=false` сохраняет все неупомянутые поля;
- `set` атомарно заменяет перечисленные поля;
- `unset` удаляет перечисленные dotted-path;
- `reset=true` сначала очищает состояние;
- `participants` заменяется целиком, чтобы старые возрасты детей не остались случайно.

Валидатор сравнивает результат применения патча с ожидаемым итоговым состоянием. Это не даёт LLM самой решать, правильно ли она сохранила условия.

## Что добавить после получения каталога

Qrels должны ссылаться только на реальные ID и конкретный снапшот каталога:

```json
{
  "query_id": "SEM-001",
  "catalog_snapshot": "<реальный-id-снапшота>",
  "event_id": "<реальный-id>",
  "occurrence_id": "<реальный-id>",
  "grade": 3,
  "hard_valid": true,
  "annotator": "<id-разметчика>"
}
```

Шкала: 0 — нерелевантно или нарушен hard; 1 — слабо связано, но hard выполнен; 2 — полезный результат; 3 — отличное соответствие. Для бинарного Recall релевантным считается grade ≥ 2.

Нельзя заполнять `occurrence_id` вымышленными значениями. Нельзя считать все неразмеченные документы нерелевантными без оговорки: это искажает Recall. Подробный pooling, event/occurrence-уровни и протокол оценки описаны в `docs/SEARCH_QUALITY.md`.
