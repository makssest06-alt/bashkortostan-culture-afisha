# Рамки продукта и MVP

Статус: черновик на основе предварительного описания задачи. Требуется сверка с полным заданием хакатона.

## Проблема

Информация о культурных событиях распределена по площадкам и может дублироваться или устаревать. Пользователю нужен единый способ найти подходящее событие, понять его актуальность и проверить источник. Внешним площадкам нужен способ использовать тот же каталог без вмешательства в действующие системы.

## Ценность

- Единый поиск по проверяемым событиям республики.
- Одинаковые данные во всех интерфейсах.
- Явные статусы и источники вместо непроверенных карточек.
- Естественный запрос вместо сложной формы фильтров.
- Открытая интеграция через REST API и виджет.

## Основные сущности

Предварительный список, не финальная схема БД:

- Event: название, описание, категория, даты, город, площадка, цена, возраст, статус, источник.
- Venue: название, адрес, координаты при наличии, город.
- Source: площадка-источник, URL, время получения, время последней проверки.
- EventStatus: запланировано, отменено, перенесено, завершено; отдельно фиксируется неопределённость данных.
- Category: единый справочник категорий и правила сопоставления источников.
- ImportRecord: происхождение записи и история обработки.
- DuplicateCandidate: возможные дубли, уверенность сопоставления и результат проверки.

## Границы MVP

### Must

1. Каталог реальных событий с источником и временем проверки.
2. Поиск и фильтры: дата, город, цена, возраст, категория.
3. Явные статусы событий.
4. Дедупликация с возможностью не объединять сомнительные записи.
5. REST API и документация.
6. Web: список, фильтры, карточка события.
7. Telegram: поиск через те же возможности API.
8. ИИ: разбор свободного запроса, уточнение недостающих условий, объяснение подборки.
9. Простой встраиваемый виджет.

### Should

- Удобный просмотр на мобильных устройствах.
- Ссылка на первоисточник и кнопка поделиться.
- Ручная проверка спорных дублей.
- Мониторинг устаревших данных.
- Healthcheck и базовая observability.

### Could

- Избранное и подписки.
- Карта событий.
- Персональные рекомендации.
- Автоматическое расписание повторного импорта.

### Won't в первой версии, если не требуется заданием

- Продажа билетов и оплата.
- Социальная сеть и отзывы.
- Обучение собственной языковой модели.
- Замена действующих систем министерства.

## Главный пользовательский сценарий

1. Пользователь пишет: «Куда пойти в субботу с ребёнком до 1000 рублей?».
2. Система определяет дату и бюджет, запрашивает город и возраст ребёнка, если они нужны.
3. Backend применяет структурированные фильтры к актуальным событиям.
4. Пользователь получает список с ценой, возрастом, местом, временем и источником.
5. Агент кратко объясняет, почему события подошли, и не выдаёт утверждений, которых нет в данных.
6. При отсутствии подходящих событий система предлагает изменить условия, а не создаёт вымышленные варианты.

## Метрики качества для проверки MVP

- Все события в демо имеют рабочий источник.
- Фильтры дают одинаковый результат в Web, Telegram и API.
- Отменённые и прошедшие события не попадают в обычную подборку.
- Известные дубли сопоставляются, спорные пары не объединяются автоматически.
- Агент задаёт уточнение при нехватке обязательных параметров.
- Каждое объяснение опирается на поля возвращённого события.
- Основной сценарий работает на мобильном экране.
