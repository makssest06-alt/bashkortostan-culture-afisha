## 1. Назначение и роль в архитектуре

В продукте «Афиша культуры Башкортостана» разделяются три вычислительных контура с чёткими границами ответственности:

1. **System 1 — `Jev` (TypeSafe AI, ~70–300 мс):** неавторегрессионный движок типизированных вероятностных решений без свободной генерации текста. Используется для мгновенной маршрутизации реплик, вероятностной классификации дублей, ИБ-скрининга недоверенного текста, оцифровки мягких предпочтений и выбора лучшего варианта строго из закрытого серверного allowlist.
2. **Deterministic Core — `PostgreSQL + Backend` (~10–25 мс):** единственный источник истины по событиям и сеансам (`Event` / `Occurrence`), проверке жёстких условий (`hard constraints`), семантике `unknown`, правам владения сессией, ревизиям и расписанию без пересечений (`no_overlap`).
3. **System 2 — `Generative LLM Structured Output` (~500–900 мс):** извлечение открытых слотов из естественного языка (относительные даты, суммы, названия, возраст) в схему `SearchConstraints` и лаконичное человекочитаемое объяснение подборки строго по полям возвращённых backend'ом записей.

```mermaid
flowchart LR
    U["Вход: текст / голос / репост афиши"] --> S1["System 1: Jev (Noul + Choice)"]
    S1 -->|"Проверка инъекций, режим хода, нужен ли 1 вопрос"| CORE["Deterministic Core (SQL + Валидаторы)"]
    U -->|"Открытые слоты: суммы, даты, сущности"| S2["System 2: LLM Structured Output"]
    S2 --> CORE
    CORE -->|"Закрытый allowlist подходящих Occurrence"| S1R["System 1: Jev (Score + Choice)"]
    S1R -->|"Мягкое ранжирование и выбор замены"| OUT["Ответ в Web / Telegram Bot API 10.4 Widget"]
```

## 2. Три примитива Jev и их инварианты

Адаптер `Jev` опирается на три базовых примитива SDK TypeSafe AI (`typesafe_sdk` / `@typesafe-ai/sdk`):

- **`Noul`** — оценка булевой гипотезы с калиброванной вероятностью истинности `0.0 .. 1.0`.
- **`Choice`** — выбор строго одного элемента из закрытого множества опций (до 255 элементов) с распределением вероятностей и `confidence`. Модель физически не может вернуть идентификатор или класс вне переданного списка.
- **`Score`** — непрерывная оценка `0.0 .. 1.0` по упорядоченной рубрике качественных уровней.

Машиночитаемый контракт ответов адаптера (включая единый формат при срабатывании `deterministic_fallback`) зафиксирован в `contracts/jev_decisions.schema.json`.

## 3. Пять рабочих контуров применения Jev

### 3.1. ИБ-экран недоверенных входов и внешних описаний (`security_guardrail`)

Связано с: `docs/SECURITY_THREAT_MODEL.md`, `security/policy_controls.json`.

Параллельный пакет `Noul`-гипотез проверяет как входящую реплику пользователя (`user_message`), так и сырые поля импортируемых карточек (`event_description`, `venue_description`, `offer_text`) до попадания их в контекст генеративной модели:

- `direct_injection_prob` — попытка переопределить системные правила, роли или формат ответа;
- `indirect_instruction_in_data_prob` — встроенные инструкции для ИИ внутри внешнего описания события или площадки;
- `secret_or_pii_probe_prob` — попытка выведать системный промпт, токены, внутренние URL или чужие сессии.

Правило безопасности: `Jev` работает как ранний фильтр и сигнал для карантина (`quarantine_for_review` / `sanitize_untrusted_text`), но **никогда не заменяет** архитектурные запреты `INV-RO` (только read-only инструменты), `INV-BACKEND-AUTHZ` и экранирование при выводе (`INV-RENDER`).

### 3.2. Мгновенный роутер диалогового хода и единственного уточнения (`session_turn_routing`)

Связано с: `docs/UX_FLOWS.md` (§5–6), `evals/ux/`.

Два параллельных вызова `Choice` на входе реплики решают главную UX-проблему многоходового куратора — отличать локальную правку условий от полной смены темы и не задавать лишних вопросов:

- `turn_mode` ∈ `{patch_keep_context, full_topic_reset, compare_selected, build_plan, explain_compromise, out_of_scope}`;
- `blocking_question` ∈ `{none, ask_city, ask_date_or_day, ask_child_age, budget_contradiction}`.

Если `blocking_question != none` и `blocking_question_confidence >= 0.70`, куратор задаёт ровно **один** короткий вопрос с готовыми чипами ответа вместо выдачи нерелевантного списка.

### 3.3. Вероятностное разрешение кандидатов в дубли (`duplicate_pair_resolution`)

Связано с: `docs/EVENT_IDENTITY.md` (§8.4–8.5), `evals/identity/`.

На старте проекта нет большой размеченной обучающей выборки для ручной калибровки весов Fellegi–Sunter. После детерминированного blocking pass (город + окно дат + нормализованные токены) спорная пара подаётся в `Jev`:

- `relation = Choice({same_occurrence, same_event_different_time, festival_subevent, series_member, different})`;
- `same_physical_venue_prob = Noul(...)`.

Таблица решений (с обязательным приоритетом детерминированных veto):

| Условие | Итоговый статус `disposition` |
|---|---|
| Есть детерминированный `hard_veto` (разные города, несовместимые даты/время для `same_occurrence`) | `separate` (или `review` для подсобытий фестиваля), автослияние запрещено |
| Нет `hard_veto`, `relation == same_occurrence`, `relation_confidence >= 0.90` и `same_physical_venue_prob >= 0.85` | `auto_merge` с сохранением обоих `SourceRecord` |
| `0.45 <= relation_confidence < 0.90` | `review` (очередь модерации с показом вероятностей) |
| `relation_confidence < 0.45` или `relation == different` с высокой уверенностью | `separate` |

### 3.4. Оцифровка мягких предпочтений и «7 лепестков курая» при импорте (`import_cultural_scoring`)

Связано с: `docs/SEARCH_QUALITY.md` (§4.3), `design/culture-kit/research/culture-brief.md`.

В официальных выгрузках афиш отсутствуют структурированные признаки атмосферы («камерно», «не шумно», «интерактивно для ребёнка», «башкирская аутентика»). При импорте карточки описание один раз оценивается в фоне:

- `kuray_petal` (`Choice` из 7 направлений цветка курая): `stage`, `heritage`, `live_sound`, `family_interactive`, `ethno_crafts`, `ideas_lectures`, `walks_routes`;
- 4 рубрики `Score`: `chamber_calm_score`, `interactivity_score`, `family_comfort_score`, `ethno_authenticity_score`.

Полученные числовые оценки сохраняются в БД рядом с `Event` как **производные сигналы ранжирования** (с явной пометкой provenance `derived_by_jev`, а не факт первоисточника). Они влияют **исключительно на порядок сортировки (`soft preferences`)** и никогда не переопределяют `hard constraints`.

### 3.5. Выбор слота замены строго из серверного allowlist (`allowlist_slot_choice`)

Связано с: `docs/CHANNELS_API.md` (§5.3), `evals/channels/`.

Когда сеанс в сохранённом плане отменён или перенесён (`plan_attention`), backend сначала отбирает через SQL только реально активные `Occurrence`, проходящие по городу, окну времени, бюджету, возрасту и отсутствию накладок с соседними пунктами плана. Их `occurrence_id` (от 1 до 255 штук) передаются как закрытый список опций в `Choice`.

Даже после ответа `Jev` backend повторно проверяет принадлежность `selected_occurrence_id ∈ candidate_occurrence_ids` и создаёт `replacement-preview`, который вступает в силу только после явного подтверждения пользователем.

## 4. Жёсткие запреты: где Jev применять нельзя

1. **Никакой проверки жёстких условий через нейросеть.** Сравнения `price <= budget_max`, `age_min <= child_age`, проверка `status == scheduled`, попадание в интервал дат и расчёт дорожных буферов выполняются только детерминированным кодом и SQL.
2. **Никакого заполнения `unknown` догадками.** Если цена или возраст не указаны в источнике, `Jev` не имеет права «угадывать» бесплатность или возрастной рейтинг (`unknown` ≠ `0` / `free` / `suitable`).
3. **Никакого парсинга открытых строк и чисел.** `Jev` не предназначен для извлечения произвольных сумм, времён или имён собственных из текста — это задача локального парсера дат/чисел и structured output модели System 2.

## 5. Надёжность, таймауты и обязательный Fallback

В соответствии с требованием отказоустойчивости (`llm_not_required_for_basic_search` в `evals/channels/` и `evals/security/`):

- вызов `Jev` в интерактивном контуре ограничивается жёстким таймаутом (`<= 600 мс`);
- при сетевой недоступности API, превышении таймаута или принудительном отключении ИИ (`JEV_ENABLED=false`) адаптер без ошибки возвращает валидный пакет по схеме `contracts/jev_decisions.schema.json` с `provider = "deterministic_fallback"`:
  - `security_guardrail` переключается на детерминированные сигнатуры и строгую санитизацию из `evals/security/policy.py`;
  - `session_turn_routing` опирается на явные поля запроса и проверку обязательных слотов;
  - `duplicate_pair_resolution` переводит нетривиальные пары без точного совпадения ключа источника в статус `review`;
  - `import_cultural_scoring` выставляет нейтральные веса `0.5` и маппинг категории по словарю;
  - `allowlist_slot_choice` выбирает первый кандидат по детерминированному SQL-рангу (близость площадки и минимальный сдвиг по времени).
