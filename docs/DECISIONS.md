### D-013. Двухсистемный ИИ-контур: System 1 (`Jev`) + Детерминированное ядро + System 2 (`LLM`)

- Дата: 2026-11-12
- Контекст: генеративная LLM избыточна, медленна и склонна к галлюцинациям на задачах закрытой классификации (маршрутизация реплик, дедупликация спорных пар, ранний скрининг prompt-injection, мягкий скоринг культурного кода, выбор слота замены из allowlist), но при этом необходима для извлечения открытых параметров запроса и связного объяснения результата.
- Решение: разделить контур на **System 1 (`Jev` от TypeSafe AI — примитивы `Noul`, `Choice`, `Score`)**, **детерминированный backend (`PostgreSQL + правила`)** и **System 2 (`LLM Structured Output`)** по контракту `contracts/jev_decisions.schema.json` и спецификации `docs/JEV_DECISION_ENGINE.md`.
- Почему: латентность 70–300 мс, калиброванные вероятности из коробки без размеченной обучающей выборки и физическая невозможность вернуть ID вне переданного закрытого списка `Choice`.
- Последствия и ограничения: `Jev` запрещено использовать для проверки жёстких условий (бюджет, возраст, расписание, `unknown`-семантика) и парсинга открытых строк/чисел; обязателен таймаут `<= 600 мс` и автоматический `deterministic_fallback` при отключении внешнего API.
- Альтернативы: гонять генеративную LLM на каждый классификационный шаг (отклонено из-за задержек и риска галлюцинаций); обучать собственные классификаторы с нуля за 48 часов (отклонено из-за отсутствия размеченного датасета).

### D-014. Двухуровневый Telegram-интерфейс с Bot API 10.4 HTML Widgets

- Дата: 2026-11-12
- Контекст: в релизе Telegram Bot API 10.4 от 2026-11-09 появились нативные HTML-виджеты внутри пузырей сообщений (`sendWidget`, `editMessageWidgetData`, `WidgetQuery`, `answerWidgetQuery`) и групповые эфемерные ответы (`ephemeral_message_parameters` без `receiver_user_id`). Классические лесенки inline-кнопок плохо подходят для управления чипами условий и живого таймлайна дня, а запуск внешнего Mini App на каждое микродействие добавляет задержку.
- Решение: реализовать в личном чате с ботом нативные **in-bubble HTML Widgets Bot API 10.4** (`docs/TELEGRAM_WIDGETS_10_4.md`, `contracts/telegram_widget_state.schema.json`) для пульта чипов/курая, сравнения до 3 сеансов и экстренной пересборки таймлайна на месте, а полноэкранный Web / Mini App открывать по кнопке для карты и полных текстов.
- Почему: нулевой холодный старт прямо в ленте сообщений и строгая офлайн-песочница QuickJS без доступа к сети (`NetworkDisabledError`), полностью совместимая с нашими 64-байтными opaque-токенами `v1:<token>` и моделью угроз `docs/SECURITY_THREAT_MODEL.md`.
- Последствия и ограничения: жёсткие лимиты `html <= 4 096` байт (`zlib -9`), `chat_data <= 1 024` байт UTF-8, высота `50–600 px` без скролла и `<input>`; в production виджеты сейчас работают только в личных чатах с ботом (`protect_content` включён автоматически), поэтому каждый вызов `sendWidget` обязан содержать текстовый `caption` и `reply_markup` fallback для старых клиентов, а в группах используются `ephemeral_message_parameters`.
- Альтернативы: только текстовые сообщения с inline-клавиатурами (уступает в UX и наглядности пересборки плана); только WebView Mini App без интерактивного пузыря в чате (теряет скорость в диалоге и преимущество свежего релиза 10.4).

### D-005, D-016, D-018. Контракт v1 по ТЗ

- Решение: событие — строго п. 8.1 (`contracts/event.schema.json`), API — `contracts/api.openapi.yaml` (OpenAPI 3.1), ошибки — `{ code, message, details, request_id }`. Сайт переводится на контракт в PR #17.

### D-008. Дедупликация — пересмотр

- Дата: 2026-11-13
- Контекст: ТЗ п. 6.5 задаёт дедупликацию по нормализованному названию, дате и площадке; п. 6.3 — одна карточка и список источников.
- Решение: `dedup_key` = `normalized_title` + местная дата начала + `venue_id`. Совпадение ключа — одна карточка, источники копятся в `sources`. Сомнительные случаи — в очередь модерации, слияние вручную через `merge`.
- Почему: детерминированно, проверяемо, укладывается в сроки.
- Последствия и ограничения: одинаковое событие с опечаткой в названии не склеится само, его сведёт модератор.
- Альтернативы: вероятностный matcher и Jev из `docs/EVENT_IDENTITY.md` и D-013 — вне скоупа.

### D-013, D-014. Пересмотр после ТЗ

- Дата: 2026-11-13
- Контекст: решения приняты 2026-11-12, до получения ТЗ. ТЗ требует агента с шестью инструментами и резервным режимом (п. 7) и Telegram-бота с инлайн-кнопками (п. 6.2). Ни Jev, ни HTML-виджеты Bot API 10.4 не требуются.
- Решение: оба решения переведены в `out_of_scope`. Базовая реализация: LLM с инструментами п. 7.2 поверх детерминированного API; бот на инлайн-кнопках и тексте.
- Почему: каждая внешняя зависимость — риск для метрик п. 9.2 и сквозного сценария. Сначала обязательное, потом улучшения.
- Последствия и ограничения: исследование сохранено. Вернуть любое из решений можно отдельным решением команды, когда уровень 3 проходит пороги.
- Альтернативы: оставить как обязательные (отклонено: не требуются ТЗ и увеличивают риск). **Нужно подтвердить командой.**

### D-015. Уровень решения

- Дата: 2026-11-13
- Контекст: ТЗ п. 5 — уровень выбирает команда и пишет в README. Оценка = баллы уровня × коэффициент качества.
- Решение: уровень 3 «Агент», запасной — уровень 2. Выбор подтверждён 2026-11-13.
- Почему: уровень 4 требует сбора из внешних источников, планировщика и 60 запросов с отчётом — большой риск за 48 часов. Уровень 3 даёт 85 баллов при выполнимом объёме.
- Последствия и ограничения: если метрики агента не проходят пороги п. 9.2, честнее сдать уровень 2.
- Альтернативы: уровень 2 сразу; уровень 4.

### D-006, D-007. Технологический стек и архитектура бэкенда

- Дата: 2026-11-13
- Контекст: в репозитории уже есть Next.js-фронтенд (`web/`, TypeScript/Node 22+) и формальные контракты v1 (`contracts/api.openapi.yaml`, `contracts/event.schema.json`, `contracts/agent_tools.json`). На хостах разработчиков и в контейнерах нужен быстрый старт без расхождения типов, а также полный PostgreSQL 16 (через Docker `postgres:16-alpine` и без внешнего сервиса БД при локальной разработке/тестах).
- Решение: реализовать бэкенд в `backend/` на **TypeScript + Hono (`@hono/node-server`) + Zod + PostgreSQL 16** через единый адаптер `backend/src/db/adapter.ts` (`pg.Pool` при `DATABASE_URL=postgresql://...` или `@electric-sql/pglite` WASM PostgreSQL 16 при пустом `DATABASE_URL` / `memory://` в Vitest).
- Почему: один язык с `web/` упрощает переиспользование схем/правил, запускается в Docker (`postgres:16-alpine` + `api` + `web` через `docker-compose.yml`) и локально из одной команды `npm ci && npm run dev`, полностью совместим и с `contracts/*`, и с UI-расширениями `web/` (`/dictionaries`, `/facets`, `/assistant/query`, `/assistant/confirm`, `/admin/applications`, `/admin/traces`).
- Последствия и ограничения: лимиты `/feedback` — 5/10 мин и 20/24 ч на `user_ref` при наличии (IP-backstop 100/10 мин), 5/10 и 20/24 ч с IP для анонимных (honeypot `website` отвечает `202` без записи в БД), лимит `/metrics` — `METRICS_RATE_LIMIT=120` в минуту на IP, срок хранения обращений — `FEEDBACK_RETENTION_DAYS=90`, неактивные подписки — 180 дней (`DELETE /subscriptions/{id}` удаляет физически). Поле `merged_into` хранится только в колонке БД `events.merged_into` и не добавляется в `event.review` (`additionalProperties: false` в `event.schema.json`).
- Альтернативы: FastAPI/Python или Go (отклонено для текущей итерации, чтобы иметь единый Node.js-стек с `web/` и нулевую настройку локального PostgreSQL через `@electric-sql/pglite`).

### D-016. Архитектура контура ИИ-агента, Telegram-бота и eval-прогона

- Дата: 2026-11-13
- Контекст: требования уровня 3 (ТЗ п. 6.2, 6.4, 7, 9.2) — агент на сайте (`/ask`) и в Telegram-боте, 6+ инструментов поверх каталога, запрет выдуманных фактов, одноразовое подтверждение мутаций, трассировка со стоимостью в ₽, резервный режим без модели и воспроизводимый отчёт метрик.
- Решение:
  1. В `backend/src/domain/assistant/` реализован двухрежимный контур (`PROMPT_VERSION = afisha-agent-v2`): OpenAI-compatible tool-calling цикл (`runLlmAgent`, лимит `MAX_TOOL_CALLS_PER_ANSWER = 5`, учёт `cost_rub`) с автоматическим переходом на детерминированный `rules-fallback-v2` при ошибке/таймауте LLM и штатным `rules-v2` при пустом `LLM_API_KEY`; фильтрация карточек строго по `grounding_ids` исключает галлюцинации, а описания событий изолируются в `<untrusted_event_data>` с очисткой `<`/`>`.
  2. Одноразовое подтверждение мутаций (`create_subscription_draft`, `delete_subscription_draft`, `save_feedback`) вынесено в `POST /api/v1/assistant/confirm` (`200` при первом вызове, `409` при повторе) и поддержано в `/ask` (`web/`) и `bot/`.
  3. Сервис `bot/` — отдельный адаптер к REST API v1 (`long polling`, HMAC `user_ref` вместо предсказуемого `telegram_<id>`, HTML-экранирование, callback-токены вместо сырых данных в `callback_data`, fallback на обычный поиск при `404`/`5xx`/таймауте ассистента). Подтверждения действий реализованы, но по умолчанию выключены до привязки confirmation-токена к `user_ref` (P0-4); доставка уведомлений по подпискам ждёт воркер в бэкенде.
  4. Единый раннер `node evals/run-evals.mjs` (`backend/scripts/run-evals.ts`) прогоняет 120 запросов `evals/search/queries.jsonl`, 25 сквозных сценариев, импорт 100 строк и сценарии ИБ `evals/security/scenarios.jsonl`, формируя `docs/EVAL_REPORT.md`.
- Почему: детерминированная проверка ограничений (дата, город, бюджет, возраст, статусы) и серверная проверка `grounding_ids` гарантируют 0 выдуманных событий и 0 показанных как активные отменённых карточек даже при галлюцинациях LLM, а единый `evals/run-evals.mjs` даёт воспроизводимый отчёт для защиты.
- Последствия и ограничения: замеры в `docs/EVAL_REPORT.md` выполняются на локальном контуре `rules-v2` + `@electric-sql/pglite` (а tool-calling LLM-цикл — на mocked OpenAI API в `backend/test/assistant.test.ts`); прогон по живому внешнему LLM требует задания `LLM_API_KEY`.
- Альтернативы: делать все запросы напрямую в LLM без детерминированного слоя слотов и фильтрации `grounding_ids` (отклонено из-за риска галлюцинаций и падения качества при отказе провайдера).
