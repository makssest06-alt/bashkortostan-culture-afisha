# UX-потоки и state contract: «ИИ-куратор культурного дня»

Продукт: «Афиша культуры Башкортостана» — ИИ-ассистент подбора культурных событий.
Поверхности: Web и Telegram над общим backend.
Статус: **спецификация UX и state contract до реализации**. Ничто в этом документе
не является утверждением о готовом UI, работающих функциях или измеренном качестве.
Связанная задача: Issue #9 (UX-исследование).

## 1. Цель, границы, связь с Issue #9

### Цель

Зафиксировать до начала реализации:

- главные UX-решения и их обоснование;
- модель состояний интерфейса (не «чат с текстом», а формальный state contract);
- session snapshot и revision binding;
- поведение в негативных сценариях (пусто, ошибки, устаревшие данные, изменения плана);
- требования к Telegram-адаптации, accessibility и security UX.

### Границы

- Это спецификация, а не дизайн-макеты и не финальная копия интерфейса: строки
  UI — контрольные формулировки, допускающие уточнение.
- Источники данных и API афиши здесь **не исследуются**: упоминания backend —
  абстрактные обязательства («backend обязан вернуть X»), не привязка к API.
- Ниже нет реальных мероприятий, `event_id`/`occurrence_id`, цен, URL событий,
  qrels и выдуманных UX-метрик. Все примеры — плейсхолдеры вида `{title}`,
  `{local_start}`, `{price_or_unknown}`.
- **Usability не измерялось.** Репозиторный набор `evals/ux/scenarios.jsonl`
  (60 сценариев, категории INT/CLR/RES/EMP/CMP/PLN/CHG/ERR/ACC/SEC) — это
  **executable contract**: фикстуры «при состоянии X интерфейс обязан показать
  A, сохранить B и не делать C», маппимые в тесты. Он проверяет структурные
  обязательства UI, но **не является usability-тестом**: время задачи, SUS,
  успешность сценариев и другие UX-метрики не измерялись и не заявляются.
- Словарь состояний и инвариантов согласован с `evals/ux/validate.py` и
  `evals/ux/README.md`; терминология ниже обязана совпадать с ним.

### Связь с Issue #9

Документ — выход UX-исследования по Issue #9: превращает продуктовые идеи
(`docs/AI_ASSISTANT_IDEAS.md`) и модель идентичности событий
(`docs/EVENT_IDENTITY.md`) в проверяемый контракт поведения интерфейса.

## 2. Десять главных UX-решений

1. **Не один чат, а диалог + рабочая область.** Свободный текст — способ ввода,
   а не единственная модель взаимодействия. Распознанные условия становятся
   видимыми редактируемыми чипами; результаты, сравнение и план живут в рабочей
   области, а не тонут в ленте сообщений.
2. **Hard constraints и soft preferences разделены везде.** Жёсткие условия
   (город, дата, возраст, бюджет, время, статус) проверяются детерминированным
   кодом; мягкие предпочтения влияют только на ранжирование и никогда не
   маскируются под факты. В UI они подписаны раздельно.
3. **SessionPatch-семантика редактирования.** Любая правка — частичное изменение:
   неупомянутые поля сохраняются. Полная перезапись сессии и смена темы — только
   явным действием пользователя (`reset`).
4. **Основная единица результата — Occurrence, а не Event.** Время, цена,
   доступность и статус привязаны к конкретному сеансу. Показ «правильного
   события с неправильной датой» считается дефектом.
5. **Unknown не равно false/0/free/«подходит».** Отсутствующая цена, возраст,
   длительность или статус показываются как «не указано» и не проходят строгие
   проверки молча. «Бесплатно» появляется только из явного утверждения источника.
6. **Честный пустой результат.** При 0 результатов исходные условия сохраняются
   и показываются; варианты ослабления предлагаются только с реальными aggregate
   counts от backend; ослабление hard-ограничений — preview + явное подтверждение.
7. **План дня — детерминированно проверяемый.** Пересечения по времени, бюджет,
   возраст и статусы перепроверяются кодом при каждом показе и изменении.
   Буфер без данных о маршруте — помеченное допущение, а не «время в пути».
8. **Saved plan immutable без accept.** Отмена/перенос occurrence переводит план
   в `plan_attention`; замена показывается как preview новой revision; исходная
   revision сохраняется; apply только по явному подтверждению.
9. **Деградация без потери состояния.** При недоступности LLM работает
   структурированный поиск с теми же чипами и формой; введённые условия не
   теряются ни при ошибках, ни при fallback.
10. **Один контракт — две поверхности.** Web и Telegram разделяют session snapshot,
    словарь состояний и текстовые эквиваленты; различаются только представлением
    (компактность, клавиатуры вместо чипов).

## 3. Модель состояний: четыре измерения

Интерфейс не находится в одном состоянии «чат». Состояние описывается четырьмя
ортогональными измерениями; это позволяет выразить, например, «результаты готовы,
но устарели, и план требует внимания» без комбинаторного взрыва.

### 3.1. Измерения

| Измерение | Значения | Смысл |
|---|---|---|
| `mode` | `search` \| `compare` \| `plan` | Что делает рабочая область: подбор, сравнение 2–3 вариантов, план дня |
| `status` | `editing` \| `clarifying` \| `loading` \| `ready` \| `empty` \| `error` \| `fallback` | Текущая фаза взаимодействия |
| `plan_state` | `none` \| `draft` \| `saved` \| `attention` | Жизненный цикл плана |
| `data_state` | `current` \| `stale` \| `partially_unknown` | Свежесть и полнота показанных данных |

Соответствие к словарю `given.state` из scenarios.jsonl: `new` — это
`status=editing` при пустой сессии; `results` — `status=ready, mode=search`;
`comparing` — `status=ready, mode=compare`; `plan` — `plan_state∈{draft,saved}`;
`plan_attention` — `plan_state=attention`.

### 3.2. Инварианты комбинаций

- `status=empty` допустим только при `mode=search` (пустой план — это
  `show_error` «план без пересечений невозможен», а не `empty`).
- `status=clarifying` означает ровно один главный вопрос; результаты в этой фазе
  не запрашиваются заново.
- `plan_state=attention` возможен только из `saved` (черновику нечего
  «устаревать»; несохранённый черновик просто пересобирается).
- `plan_state≠none` допустим только при `mode=plan` или при наличии баннера
  «план требует внимания» поверх другого mode (баннер не меняет mode).
- `data_state=stale` допустим только при `status=ready`: устаревшими могут быть
  показанные результаты или сохранённый план, но не экран редактирования.
- `data_state=partially_unknown` — свойство выдачи (у части карточек поля
  неизвестны); не блокирует `ready`, но требует пометок «не указано».
- `status=fallback` не меняет `mode` и `plan_state`: LLM-недоступность не
  уничтожает сессию и план.

### 3.3. Ключевые переходы

```text
new/editing --[submit, обязательные условия есть]--> loading
new/editing --[submit, нужен ответ для допустимости]--> clarifying
clarifying --[ответ получен]--> editing | loading
loading --[ok, результаты]--> ready
loading --[ok, 0 результатов]--> empty
loading --[ошибка/таймаут]--> error --[retry, идемпотентно]--> loading
error --[«Изменить условия»]--> editing
loading --[LLM недоступен]--> fallback (structured search, условия сохранены)
fallback --[«Искать снова»]--> loading
empty --[preview_relaxation + явный confirm]--> loading
empty --[«Изменить условия»]--> editing
empty --[«Оставить условия» / отказ от ослабления]--> empty
ready --[выбраны 2–3 варианта]--> ready(mode=compare)
ready --[«собрать план», backend может]--> plan_state=draft
draft --[«сохранить», успех]--> plan_state=saved
saved --[фоновое/ручное обнаружение отмены/переноса]--> plan_state=attention
attention --[preview новой revision]--> attention (ожидание решения)
attention --[accept]--> saved (новая revision, старая сохранена)
attention --[reject]--> attention (старая revision, предупреждение остаётся)
ready --[условия изменены без перезапуска]--> ready(data_state=stale) + баннер
```

Любой переход в `error`/`fallback` обязан сохранить `mode`, `plan_state` и все
введённые условия (`no_dead_controls`, `preserve_unmentioned_constraints`).

## 4. Session snapshot и revision binding

### 4.1. Контракт снимка сессии

Единый серверный снимок, общий для Web и Telegram:

```json
{
  "session_revision": 7,
  "mode": "search",
  "status": "ready",
  "hard_constraints": {
    "city": {"value": "{city}", "source": "user"},
    "date": {"value": "{date}", "source": "user"},
    "max_budget": {"value": "{amount_or_null}", "source": "user"},
    "participants_age": {"value": "{age_or_null}", "source": "user"}
  },
  "soft_preferences": {
    "{preference_key}": {"value": "{value}", "source": "llm_interpretation"}
  },
  "assumptions": [
    {"key": "late_evening", "assumed": "окончание до {time}", "editable": true}
  ],
  "pending_question": null,
  "result_revision": 3,
  "result_occurrence_ids": ["{occurrence_id_1}", "{occurrence_id_2}"],
  "plan_revision": null,
  "plan_state": "none",
  "data_state": "current"
}
```

Правила полей:

- Каждое ограничение хранит `value` и `source` (`user` | `llm_interpretation` |
  `assumption`), чтобы UI отличал подтверждённое пользователем от догадки.
- `assumptions` — явный список допущений («"не поздно" понято как окончание до
  {time}»), каждое редактируемо и отменяемо.
- `pending_question` — не более одного; следующий вопрос заменяет предыдущий.
- `result_occurrence_ids` — только ID из последнего разрешённого поиска backend;
  это allowlist для действий над поисковой выдачей (детали, сравнение, запуск
  построения плана). Кандидаты из отдельного ответа `build_plan` или preview замены
  проверяются против allowlist и revision того ответа, а не считаются автоматически
  частью поисковой выдачи.

### 4.2. Revision binding и защита от stale response

- `session_revision` монотонно растёт с каждым принятым SessionPatch; каждый
  запрос к backend несёт `session_revision`, на котором он инициирован.
- Ответ backend привязан к `result_revision` и `session_revision` запроса.
  Поздний ответ к устаревшей `session_revision` **не заменяет выдачу более новой
  revision**. Если пользователь изменил условия после показа прежней выдачи, именно
  прежняя видимая выдача помечается `data_state=stale` с баннером «результаты
  устарели для новых условий» и кнопкой «Обновить результаты».
- Действия над результатами (сравнить, в план, подробнее) валидны только для
  ID из текущего `result_occurrence_ids`. Чужой ID отклоняется сообщением
  «объект не относится к текущим результатам» — без выдумывания данных. Из stale
  выдачи можно открыть справочные детали, но нельзя запустить сравнение или новый
  план как будто она соответствует новым условиям: сначала требуется обновление.
- `plan_revision` аналогично: любая принятая мутация плана создаёт новую revision,
  старая остаётся читаемой (append-only со стороны UX). `plan_state=none` требует
  `plan_revision=null`. Accept замены привязан к конкретной preview revision и её
  разрешённым occurrence IDs; повторный или устаревший accept не применяется.

### 4.3. Граница синхронизации аккаунтов

Снимок сессии привязан к поверхности и аккаунту, на которых он создан.
**Не обещается** автоматическая синхронизация состояния между Web- и
Telegram-аккаунтами незнакомых пользователей: до появления подтверждённого
механизма связки аккаунтов каждая поверхность работает со своей сессией.
Единое — контракт состояний и текстов, а не магическая склейка identity.

## 5. Первый запрос и редактирование условий

### 5.1. Конвейер ввода

```text
свободный текст пользователя
  → LLM: намерение + черновой SessionPatch + мягкие предпочтения
  → backend: валидация по схеме, нормализация дат/диапазонов, права
  → validated SessionPatch (применяется) + assumptions (показываются)
  → UI: обновлённые чипы hard/soft условий + список допущений
```

Модель никогда не возвращает весь фильтр заново — только изменение состояния.
Факты в карточках и таймлайне строятся кодом из данных backend; LLM не
переписывает название, цену, адрес, дату и ссылку.

### 5.2. SessionPatch-семантика

```json
{"set": {"max_budget": "{amount}"}, "clear": [], "keep": ["city", "date"]}
```

- `set` — изменить перечисленные поля; `clear` — перевести поля в `unknown`;
  `keep` — явно подтвердить сохранение. По умолчанию сохраняется всё
  неупомянутое (`preserve_unmentioned_constraints`).
- **clear → unknown, а не «всё подходит».** Очищенный бюджет показывается как
  «не указано» с подсказкой «поиск без фильтра по бюджету»; очищенное поле не
  считается молча удовлетворённым (`unknown_not_satisfied`).
- **reset — только явный.** Смена темы («теперь в другое место») не стирает
  город/дату/возраст без явного «Сбросить всё» или эквивалентной команды.
  Фраза «а бесплатно что-нибудь есть?» обязана изменить только бюджет.
- Условия из `llm_interpretation` помечаются как распознанные; правка чипа
  повышает `source` до `user`.
- Каждое допущение модели показывается с возможностью правки: «Понял “не поздно”
  как окончание до {time} — изменить?»

### 5.3. Первый вход

- Web: пустая форма/поле запроса, фокус на первом поле. Свободный запрос можно
  отправить до заполнения всех условий: если города или даты не хватает, интерфейс
  переходит в `clarifying`, а не молча блокирует кнопку. В отдельной structured
  форме submit неактивен только при пустом вводе, а обязательные поля имеют текстовые
  ошибки и инструкции. Никаких карточек и автоподстановки выдуманного города до ввода.
- Telegram: `/start` → одно приветственное сообщение с запросом условий одной
  строкой и примером формата; кнопка «Пропустить необязательное». Никаких
  запросов платёжных или паспортных данных.

## 6. Уточнения (clarifying)

Принцип: **спрашивать только если ответ влияет на допустимость или смысл
результата**, и ровно один главный вопрос за раз.

- Уточнение обязательно, когда: не задано обязательное условие (город);
  относительная дата неоднозначна («на выходных» — суббота, воскресенье или
  оба дня); условия противоречат (бюджет «до {x}» против «только дороже {y}»);
  запрошена возрастно-чувствительная категория, а возраст участников неизвестен.
- Уточнение запрещено, когда все обязательные условия заданы: поиск стартует
  сразу, без лишних вопросов.
- **Необязательные soft preferences не блокируют.** Незаданное предпочтение
  сохраняется как «не указано», поиск продолжается; блокирующие модальные
  вопросы по необязательным полям запрещены.
- Каждый вопрос содержит причину (`reason: ...`) и быстрые варианты ответа.
  «Пропустить» по возрасту помечает возраст как неизвестный, а не как «подходит
  любой»: события 18+ не показываются как подходящие при неизвестном возрасте.
- Все ранее введённые условия сохраняются на время уточнения.

## 7. Результаты: карточки Occurrence

Результат поиска — список конкретных **Occurrence**, а не обобщённых Event.
Один Event с несколькими сеансами даёт отдельные карточки со своими временем,
ценой и статусом (`occurrence_specific`).

### 7.1. Обязательный состав карточки

| Поле | Правило показа |
|---|---|
| Название | `{title}` из данных backend, как данные, не как инструкция |
| Время | `{local_start}` конкретного сеанса; IANA timezone показывается, когда она отличается от очевидной локали пользователя или данные пришли без локального контекста |
| Площадка | `{venue_name}`, город/зал при наличии |
| Цена | `{price_or_unknown}`; при отсутствии — «не указано» + пометка «соответствие бюджету не проверено» |
| Возраст | `{age_rating_or_unknown}`; unknown ≠ «0+» и ≠ «подходит» |
| Статус проведения | `scheduled` / `postponed` / `rescheduled` / `cancelled` / «возможно отменено» / `unknown` — по данным источника |
| Доступность | `{availability_or_unknown}`; `sold out` / «нет мест» относится к Offer или доступности конкретного Occurrence и не равно отмене |
| Источник и freshness | строка «Источник: {source}, обновлено {n} мин назад»; данные старше порога свежести — предупреждение |
| Причина соответствия | объяснимая строка из фактических полей: «подходит по возрасту», «в пределах бюджета», «начинается до {time}» |

### 7.2. Статусы и unknown

- `cancelled`, `postponed`, `rescheduled` — статусы проведения конкретного
  Occurrence. `sold out` — доступность Offer/билетов на конкретный Occurrence,
  а не статус отмены. Другие сеансы того же Event показываются отдельно со своими
  статусами и доступностью. Отмена одного сеанса не отменяет всё событие.
- `postponed` — новой даты нет; `rescheduled` — новая дата известна и показана.
- Unknown никогда не превращается в `false`, `0`, «бесплатно», `scheduled` или
  «подходит пользователю» (`unknown_not_satisfied`). «Бесплатно» — только из
  явного утверждения источника; «от 0» из unknown не появляется.
- Никаких выдуманных значений: время, цена, длительность и статус берутся только
  из backend (`no_fabricated_events`).
- «Подробнее об источнике»: название источника, дата-время получения данных,
  статус occurrence по источнику, предупреждение о давности. Данные источника
  read-only — редактирования из интерфейса нет.

## 8. Пустой результат (empty)

При 0 результатах интерфейс обязан:

1. Показать сообщение «по заданным условиям ничего не найдено».
2. Показать **исходные условия как заданы** (`constraints: город, дата, бюджет,
   возраст — перечислены`) — они не меняются и не стираются.
3. Дать кнопку «Изменить условия».

### Варианты ослабления

- Предлагаются только с **aggregate counts backend** («дата ±1 день → {n}»,
  «бюджет выше → {m}»). Числа вычисляются реальными агрегатными запросами, а не
  моделью (`backend_counts_only`).
- Если counts недоступны (ошибка агрегации) — список возможных ослаблений
  показывается **без чисел**; оценки вида «наверняка что-то найдётся» запрещены.
- Ослабление hard-ограничения — всегда preview + явное подтверждение
  (`confirm: «Применить выбранное ослабление»`); применение до подтверждения и
  молчаливое ослабление запрещены (`no_silent_hard_relaxation`).
- Жёсткие условия и мягкие предпочтения в списке ослаблений подписаны раздельно.
- **Возрастные и другие критичные ограничения не предлагаются к ослаблению как
  обычный фильтр** и не ослабляются автоматически ради «красивого» ответа.
- Отказ от всех вариантов («Оставить условия») — валидный исход: условия
  сохранены, результат по-прежнему пуст, «Изменить условия» доступна.

## 9. Сравнение (compare)

- Сравниваются 2–3 конкретных Occurrence. Запрос на большее число → уточнение
  «выберите 2–3 варианта» с причиной, а не нечитаемая таблица из пяти колонок.
- Таблица по ключевым полям: время occurrence, цена, возрастное ограничение,
  длительность, статус, источник и freshness каждого варианта.
- Unknown показывается как «не указано» (`unknown_rendered_as_unspecified`);
  сравнение выполняется только по доступным полям, что подписывается явно.
- **Нет автоматического победителя** (`no_invented_winner`): ни бейджа
  «лучший вариант», ни подсветки «выгоднее» при неизвестной цене, ни сортировки
  «по уму» без объяснимого критерия. На вопрос «какой лучше» без заданного
  критерия — разбор компромиссов (цена против времени и возрастного
  ограничения) и приглашение задать критерий.
- При несопоставимой freshness источников (данные по варианту B старше) —
  предупреждение и никакого вывода о победителе: сравнивать несвежие данные как
  равноправные нельзя.

## 10. План дня (plan)

### 10.1. Когда план предлагается

- Варианты плана («Спокойный», «Насыщенный», «Минимум поездок» — 2–3 стиля)
  показываются **только если backend реально может построить план** при текущих
  условиях. Если построить нельзя — честное сообщение, а не кнопка-пустышка.
- План строится кодом: жёсткий фильтр → ограниченный набор кандидатов →
  перебор комбинаций и порядков → отбраковка пересечений → проверка бюджета и
  возраста → ранжирование по мягким предпочтениям. LLM не строит расписание и
  не вычисляет его выполнимость.

### 10.2. Детерминированные проверки при показе и изменении

- `no_overlap`: пункты плана не пересекаются по времени (с учётом буферов).
- `budget_rechecked`: итог по бюджету пересчитывается из цен конкретных
  occurrence при каждом показе и замене пункта; показана сумма и лимит.
- `age_rechecked`: возрастные ограничения перепроверены у каждого пункта;
  конфликт (например, пункт {12+} при участнике {age} лет) показывается
  предупреждением с кнопкой «Заменить пункт», а не скрывается.
- Статусы occurrence и доступность Offer в плане перепроверяются при открытии плана.
- Неизвестная цена, возраст, длительность или доступность не дают права заявить,
  что все hard constraints выполнены. Такой план либо не строится по строгому
  условию, либо показывается как неверифицированный с конкретной причиной — без
  бейджа «всё проверено».
- Каждый пункт привязан к конкретному occurrence; время вида «ориентировочно
  днём» без привязки запрещено.

### 10.3. Буферы и допущения

- Если данных о маршруте нет, между пунктами ставится честно помеченный
  временной буфер («буфер {n} мин — допущение»), а не выдуманное «время в пути»
  (`buffers_marked_as_assumptions`).
- Неизвестная длительность пункта → допущение с явной меткой («длительность —
  допущение {n} мин»). Допущение без пометки запрещено.

### 10.4. No feasible plan

Если план без пересечений невозможен при текущих условиях — это `show_error`,
а не «план впритык»: сообщение о невозможности, список конфликтующих
интервалов, кнопка «Изменить условия». План с наложением без пометки запрещён.

## 11. Сохранённый план и изменения

### 11.1. Неизменяемость и revisions

- Saved plan **immutable без accept**: ни фоновое обновление, ни предложение
  backend не меняют сохранённую revision молча (`original_plan_retained`,
  `user_confirms_plan_revision`).
- Каждая принятая замена создаёт **новую revision**; предыдущая остаётся
  доступной по ссылке «Предыдущая версия плана».

### 11.2. Поток plan_attention

```text
источник сообщает: occurrence отменён/перенесён
  → plan_state: saved → attention
  → баннер «план требует внимания» + объявление (не крадёт фокус)
  → текущая revision показана без изменений, отменённый пункт помечен
  → действия: «Подобрать замену» | «Оставить как есть»
  → backend нашёл замену → preview различий новой revision
       (неизменённые пункты сохранены: unaffected_plan_items_preserved)
  → accept → saved(новая revision), старая revision доступна
  → reject → attention(старая revision), предложенная candidate revision отклонена;
             предупреждение «требует внимания» остаётся до принятия новой валидной revision
```

- «Оставить как есть» и «Отклонить замену» сохраняют исходную revision в
  `plan_state=attention`; они не подтверждают выполнимость отменённого пункта.
  Вернуться в `saved` можно через принятие проверенной новой revision, включая
  явно подтверждённое удаление проблемного пункта с пересчётом всего плана.
- Ручной перенос пункта на другой occurrence — тот же поток: preview нового
  времени и пересчитанных буферов, проверка `no_overlap`, затем
  `confirm: «Применить перенос»`. Сдвиг других пунктов без пометки запрещён.
- **Cancellation Occurrence ≠ cancellation Event**: отменён конкретный сеанс;
  другие сеансы того же события могут оставаться валидными кандидатами на
  замену — это решает backend по статусам, а не предположение UI.
- Фоновое уведомление не перехватывает фокус и не активируется само: баннер +
  точечное объявление; переход к плану — только по действию пользователя.

## 12. Loading, error, stale, fallback, retry

| Состояние | Поведение |
|---|---|
| `loading` | Индикатор + текст «ищем по условиям: {город, дата, бюджет, возраст}»; объявление «поиск начался»; повторный submit заблокирован |
| `error` (таймаут, 5xx) | Сообщение простым языком без stack trace и внутренних деталей; обезличенный код обращения для поддержки; условия на месте; кнопка «Повторить» |
| `error` (сохранение плана не удалось) | «План не сохранён», черновик без изменений, «Повторить сохранение»; сообщение «сохранено» при ошибке запрещено |
| `fallback` (LLM недоступен / невалидный ответ) | «Умный помощник временно недоступен»; обычная структурированная форма поиска работает (`llm_not_required_for_basic_search`); введённые условия сохранены; сырой неструктурированный текст LLM не показывается как результат; кнопка «Искать снова» |
| `stale` | Условия изменены после показа результатов → баннер «результаты устарели для новых условий», рядом новые условия и условия выдачи, кнопка «Обновить результаты»; старые результаты не выдаются за актуальные без пометки (`stale_output_marked`) |

### Retry и идемпотентность

- Каждая mutating/поисковая операция несёт идемпотентный ключ; повторный клик
  по «Повторить» во время выполнения не порождает дубль запроса или запись
  (`idempotent_retry`). Кнопка retry показывает индикатор выполнения и
  блокируется до завершения.
- В error/fallback нет мёртвых контролов (`no_dead_controls`): каждый видимый
  элемент либо работает, либо явно объяснено, почему он недоступен.
- Ошибки в UI sanitised: никаких stack trace, ключей API, секретов и
  персональных данных (`no_sensitive_data`, см. §17).

## 14. Telegram-поверхность

- **Компактное summary message.** Результаты — одно сообщение-сводка
  (условия, {n} вариантов, верхние карточки в сжатом виде) с клавиатурой
  действий, а не бесконечная лента из отдельных сообщений на каждую карточку.
  Раскрытие деталей — по кнопке.
- **Callback acknowledgement обязателен.** На каждый callback_query — ответ
  (toast/текст). Молчание на нажатие запрещено.
- **Callback data — opaque short action token**, не ID события и не
  сериализованное состояние. Сервер хранит mapping token → действие в рамках
  session/revision allowlist; ID из клиента не доверяются: токен, не входящий
  в allowlist текущей сессии/revision, отклоняется.
- **Stale callback**: acknowledge + понятное сообщение «эта кнопка устарела» +
  свежая клавиатура с актуальными действиями. Зависание диалога запрещено
  (`callback_expiry_graceful`).
- **Edit failures → новое сообщение.** Если редактирование исходного сообщения
  не удалось (устарело, удалено), бот отправляет новое сообщение вместо
  молчаливого провала.
- **Текстовые команды-эквиваленты** для каждого действия клавиатуры
  («сравнить 1 и 2», «изменить бюджет», «обновить»): всё, что можно нажать,
  можно написать (`keyboard_operable` переносится на текстовый ввод).
- **Не обещать оплату/покупку.** Никаких кнопок «Купить», «Забронировать»;
  на запрос покупки — вежливый отказ и предложение показать детали occurrence.
- **Mini App — только отложенная опция.** Не входит в контракт MVP; решение
  принимается после официального задания.

## 15. Accessibility (Web) и текстовые эквиваленты (Telegram)

### Web (WCAG 2.2)

- **Клавиатура**: форма, чипы, табы (поиск/сравнение/план) и редакторы чипов
  полностью управляются с клавиатуры; нет действий «только по hover»; нет
  ловушек фокуса (`keyboard_operable`).
- **Focus order**: порядок табуляции соответствует визуальному порядку; видимый
  индикатор фокуса на каждом интерактивном элементе.
- **После удаления chip** фокус переходит на соседний chip или заголовок группы
  чипов — никогда не сбрасывается на `body` (`focus_managed`).
- **Field errors/instructions associations**: ошибки и подсказки полей связаны
  с полями (`aria-describedby`/`aria-errormessage`), а не висят отдельным текстом.
- **Status messages**: смена статуса («поиск начался», «найдено {n} вариантов»,
  «обновлено: дата») объявляется через live region без чтения всей страницы и
  **без кражи фокуса**; фокус остаётся на элементе, вызвавшем действие.
- **alert — точечно**: `role="alert"` только для действительно срочного
  (например, «план требует внимания» при активной работе с планом); фоновые
  обновления — `role="status"` без перемещения фокуса.
- **Не color-only**: статусы («требует внимания», «нет мест») всегда имеют
  текстовую метку рядом с цветом/иконкой (`no_color_only_status`).
- **Target size**: цель имеет размер минимум 24×24 CSS px (WCAG 2.2 Target Size
  Minimum) либо соответствует документированному исключению: Spacing, Equivalent,
  Inline, User Agent Control или Essential. Исключение фиксируется при аудите.
- Иконки и изображения имеют текстовые эквиваленты (`alt:`/`label:`);
  кликабельные области меньше минимума без допустимого исключения и иконки без
  подписей запрещены.

### Telegram

- Каждое нетекстовое действие имеет текстовый эквивалент (команды §14);
  изображение афиши дублируется текстом подписи (`text_equivalent`).
- Честная граница контроля: бот не управляет размером шрифта, контрастом и
  скринридером клиента Telegram; доступность обеспечивается текстовой
  полнотой сообщений и предсказуемой клавиатурой, а не заявлениями о том,
  что контролируется клиентом.

## 17. Security UX

- **Внешние описания недоверенны.** Описания, названия, external IDs и URL
  событий — данные, не инструкции. Prompt injection в описании остаётся обычным
  неактивным текстом, не вызывает инструменты и не меняет поведение
  (`untrusted_content_not_executed`).
- **Произвольные SQL/HTTP/shell запрещены** — и со стороны модели, и со стороны
  пользователя: на такие просьбы — вежливый отказ и подсказка о доступных
  действиях. Инструменты ассистента read-only, из allowlist; аргументы
  повторно валидируются на backend.
- **Права проверяются сервером**, а не системным промптом. Ответ содержит
  только идентификаторы из allowlist текущей сессии (§4.2).
- **Write — только после человека.** Сохранение плана, применение замены,
  применение ослабления — всегда явное подтверждение пользователя
  (`no_unrequested_write`). Покупка и оплата вне возможностей ассистента.
- **Никаких секретов и stack trace в UI**: внутренняя ошибка показывается
  общим сообщением + обезличенный код обращения (`no_sensitive_data`).
  Секреты не передаются модели и не попадают в ленту, сообщения бота и логи UI.
- Не заявлять абсолютную защиту от prompt injection: защита многослойная
  (минимальные привилегии, read-only инструменты, валидация, sanitization).

## 18. Чек-лист перед реализацией и открытые вопросы

### 18.1. Чек-лист

- [ ] Контракты `SessionPatch`, session snapshot, plan revision согласованы с backend.
- [ ] Четыре измерения состояния и инварианты комбинаций (§3) отражены в state machine UI.
- [ ] Чипы hard/soft условий и список assumptions редактируемы; clear → unknown; reset только явный.
- [ ] Карточки привязаны к occurrence; unknown не превращается в false/0/free/«подходит».
- [ ] Empty-поток: исходные условия сохранены, counts только от backend, relax — preview + confirm; критичные возрастные ограничения не ослабляются.
- [ ] Сравнение 2–3, «не указано», без выдуманного победителя и при разной freshness.
- [ ] План: `no_overlap`/`budget_rechecked`/`age_rechecked` кодом; буферы помечены как допущения; no feasible plan — честный error.
- [ ] Saved plan immutable; attention → preview → accept/reject; старая revision доступна.
- [ ] Retry идемпотентен; error/fallback без мёртвых контролов и без потери условий; stale помечен.
- [ ] Telegram: ack на каждый callback, opaque short tokens, серверный allowlist, stale callback → новое сообщение, текстовые эквиваленты команд.
- [ ] Accessibility: keyboard, focus management, live regions, не color-only, 24×24 px target.
- [ ] Все 60 сценариев `evals/ux/scenarios.jsonl` маппятся в тесты; валидатор зелёный; отчёт честно фиксирует: **usability не измерялось**.
