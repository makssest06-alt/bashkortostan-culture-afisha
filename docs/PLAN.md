## Как работаем параллельно

Контракт v1 готов до кода, поэтому фронт, бэк и бот стартуют одновременно.

- **Фронт** работает на моках, которые проходят `event.schema.json` (примеры есть в `examples`). Типы лучше генерировать из `api.openapi.yaml`, а не писать руками.
- **Бэк** проверяет в тестах, что реальные ответы проходят те же схемы, включая пустую выдачу, ошибки и отменённое событие.
- **Бот** вызывает API только через инструменты из `agent_tools.json`.
- **Изменение контракта:** сначала PR в `contracts/` с ревью всех трёх сторон, потом код. Поле, которого нет в контракте, никто не отдаёт и ни на что не опирается.
- Проверка спеки: `npx --yes @redocly/cli@1 lint contracts/api.openapi.yaml`.

## Порядок работы

Порядок повторяет уровни ТЗ: каждый следующий этап включает предыдущий, и на любом этапе есть что сдать.

### Этап 0. Контракт — готово

ТЗ в репозитории, соответствие ТЗ, схема события, OpenAPI, инструменты агента, решения. Осталось: назначить владельцев и зафиксировать уровень.

### Этап 1. Сквозной минимум и уровень 1

- Бэк: БД с миграциями, импорт CSV/JSON с отчётом, `GET /events`, `GET /events/{id}`, справочники, подписки. `docker-compose.yml` и `.env.example` — сразу, а не в конце.
- Бот: `/start` с меню на инлайн-кнопках, поиск, карточка, «показать ещё», подписка и отписка, `/help`, `/cancel`, свободный текст как поиск.
- Данные: подготовленный набор заказчика, если передан. Если нет — синтетический набор с `synthetic: true` и честной пометкой.

Готово, когда: `docker compose up` поднимает всё на чистой машине, сценарий «запрос → карточка → подписка» проходит в боте.

### Этап 2. Уровень 2

- Фронт: сайт на реальном API вместо заглушек, фильтры в адресной строке, отменённое событие, блок «Источники», форма заявки, параметры виджета (город, категория, период, высота), админка, доступность. Всё это уже делается в PR #17.
- Бэк: дедупликация по `dedup_key`, очередь модерации, правка с `If-Match`, журнал, `ETag`, лимит частоты, `/health`, `/metrics`, `POST /feedback`.

Готово, когда: пороги п. 9.1 проверены на наборе данных, импорт файла на 100 событий проходит без дублей.

### Этап 3. Уровень 3

- Бот: агент с шестью инструментами, уточнения, память пяти реплик, объяснение «почему подходит», трассы, резервный режим, лимит пяти шагов, подтверждение изменений.
- Фронт: `/ask` на агенте, видно, что ответ собран по данным афиши, видно режим `fallback`.
- Бот: 20 контрольных запросов по типам Приложения А и первые метрики п. 9.2 (по п. 12 этого достаточно для уровня 3). Основа — `evals/search/` и `evals/security/`.
- README: модель, стоимость диалога и способ расчёта.

Готово, когда: метрики агента проходят пороги уровня 3. Если нет — сдаём уровень 2 (см. «Риски»).

### Заморозка

За несколько часов до сдачи новые функции не начинаем: только исправления, проверка сценария, демо на 5 минут и запасная запись экрана.

## Критерии готовности к сдаче

- `docker compose up` на чистой машине, до 10 минут по README.
- Сквозной сценарий: запрос → уточнение → карточка → подписка — в боте и на сайте.
- Ни одного выдуманного мероприятия. Демо-данные помечены.
- Резервный режим показан вживую.
- README: уровень, архитектура, запуск, модель, стоимость диалога, срок хранения подписок, ограничения.
- OpenAPI, примеры curl, записка о решении, сценарий демо.

## Риски и запасной план

| Риск | Что делаем |
|---|---|
| Набор событий заказчика не придёт или придёт поздно | Синтетический набор с `synthetic: true`, механизм импорта и дедупликации показываем на нём |
| Модель недоступна на демо | Резервный режим — обязательная часть демо, не авария |
| Метрики агента не проходят пороги п. 9.2 | Сдаём уровень 2: аккуратный уровень 2 может обойти уровень 3 с проваленными метриками |
| Сайт и бэк разъехались по полям | Контракт v1 и проверка ответов по схемам в тестах |
| Нет времени на всё | Порядок этапов: на любом этапе есть рабочий результат |

## Что сознательно не делаем

- Уровень 4: сбор из внешних источников, планировщик «Выходной день», 60 запросов с отчётом — пока команда не выберет этот уровень.
- Билеты, оплату, мобильные приложения, изменения в системах министерства (ТЗ п. 11).
- Исследовательские схемы из раздела «Вне скоупа хакатона» в `docs/DECISIONS.md`: многосущностная модель идентичности, сессии с осями ревизий, Jev, HTML-виджеты Bot API 10.4.
- Микросервисы и обучение собственной модели.
