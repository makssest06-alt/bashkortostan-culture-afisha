# План подготовки и работы

Статус: предварительный план до уточнения официального задания, состава команды и критериев оценки.

## Цель подготовки

К началу хакатона команда должна понимать продукт, иметь согласованный MVP, проверенные источники данных, выбранную архитектуру, рабочий репозиторий и реалистичный план демонстрации. Не пытаемся заранее реализовать весь продукт.

## Этап 0. Запуск команды

Результат: всем участникам выдан доступ, назначены владельцы направлений, есть общий список открытых решений.

Предлагаемые роли, которые можно совмещать:

| Направление | Ответственность |
|---|---|
| Продукт и координация | Требования, приоритеты, задание, сроки, коммуникация |
| Данные | Источники, схема, импорт, качество, статусы, дедупликация |
| Backend и API | Доменная модель, REST API, поиск, интеграции |
| Web и дизайн | UX, интерфейс, адаптивность, виджет |
| Telegram и ИИ | Bot API 10.4 HTML Widgets, System 1 (`Jev`), System 2 (`LLM`), уточнения, объяснения |
| QA и демо | Проверки, тестовые сценарии, презентация, запасной план |

## День 1. Исследование и проектирование

### 1. Уточнить рамки задачи

- Перенести полное официальное задание и критерии оценки в репозиторий.
- Выделить обязательные требования и конкурентные преимущества.
- Зафиксировать ограничения по данным, срокам, развёртыванию и доступам.

Результат: актуальный `docs/PRODUCT.md`, список вопросов организаторам.

### 2. Исследовать аналоги и подходы

Направления:

- региональные и федеральные афиши;
- агрегаторы событий и их фильтры;
- Telegram-боты событий и нативные HTML-виджеты Bot API 10.4;
- открытые API, виджеты и схемы интеграции;
- дедупликация событий и контроль актуальности;
- преобразование естественного языка в структурированный поиск и типизированные вероятностные решения (`Jev`).

Результат: сравнительная таблица решений со ссылками, сильными и слабыми сторонами, список практик, которые применимы к задаче. Подробности — в `docs/RESEARCH.md`, `docs/JEV_DECISION_ENGINE.md` и `docs/TELEGRAM_WIDGETS_10_4.md`.

### 3. Согласовать MVP и демонстрационный сценарий

Черновой приоритет Must:

- единый каталог проверяемых событий и сеансов (`Occurrence`);
- детерминированный поиск и жёсткие фильтры по дате, городу, цене, возрасту, категории и статусу;
- статусы сеанса, признак последней проверки и пересборка плана при отмене (`plan_attention`);
- REST API;
- веб-список, чипы условий, план дня и карточка события;
- Telegram-сценарий на базе нативных in-bubble HTML-виджетов **Bot API 10.4** (`sendWidget` + `editMessageWidgetData` + `WidgetQuery`) с `caption`/`reply_markup` fallback и тем же API;
- двухсистемный ИИ-контур: System 1 (`Jev` — роутинг хода, ИБ-скрининг, мягкий скоринг, выбор замены из allowlist) + System 2 (`LLM Structured Output` — разбор свободного запроса и объяснение подборки) + fallback без ИИ;
- дедупликация с детерминированными veto и вероятностной оценкой спорных пар через `Jev`;
- документация подключения и простой партнёрский веб-виджет.

Should и Could определяем только после исследования и оценки ресурсов.

Результат: один главный сценарий демо, например: пользователь спрашивает «куда пойти в субботу с ребёнком до 1000 рублей», куратор через `Jev` определяет недостающие слоты, уточняет город и возраст, строит план из проверенных `Occurrence`, рендерит его прямо в пузыре Telegram-виджета и при экстренной отмене одного из сеансов предлагает подтверждаемую замену.

### 4. Спроектировать архитектуру

Согласованный контур (см. `docs/DECISIONS.md` D-013, D-014, `docs/JEV_DECISION_ENGINE.md`, `docs/TELEGRAM_WIDGETS_10_4.md`):

```text
Источники → импорт + нормализация + Jev (ИБ-скрининг, дубли, мягкий скоринг) → PostgreSQL
                                                                                   ↓
                                                                   Детерминированный Backend / REST API
                                                                   ↓                 ↓               ↓
                                                                  Web    Telegram (Bot API 10.4    Внешний
                                                                         HTML Widgets + fallback)  веб-виджет
                                                                   ↖                 ↗
                                                    System 1 (Jev: роутинг / allowlist Choice)
                                                  + System 2 (LLM: открытые слоты / объяснения)
```

- Сайт, Telegram-виджеты и внешний партнёрский виджет не имеют собственных копий каталога.
- System 1 (`Jev`) решает закрытые вероятностные задачи за ~70–300 мс (`Noul`, `Choice`, `Score`), System 2 (`LLM`) извлекает открытые параметры и формулирует объяснения, а все жёсткие фильтры, бюджеты, расписания и права сессии проверяет детерминированный backend.
- При отключении `Jev` или `LLM` срабатывает `deterministic_fallback`, сохраняя работоспособность структурированного поиска и проверки плана.
- В Telegram для личного чата используются нативные in-bubble HTML-виджеты Bot API 10.4 (`<= 4 096` байт `zlib -9`, офлайн-песочница QuickJS, `chat_data <= 1 024` байт UTF-8) с обязательным `caption` + `reply_markup` fallback и переходом в Web/Mini App для полной карты.
- Импорт, валидация, статусы и дедупликация — отдельный проверяемый контур.
- Для хакатона предпочтителен модульный монолит, если исследование не покажет необходимость иного.

Результат: схема компонентов, контракты событий, решений `Jev` и состояния Telegram-виджета (`contracts/`), основные API endpoints, план развёртывания, ADR по ключевым решениям.

### 5. Подготовить UX-каркас

- Главная страница и поиск.
- Чипы жёстких/мягких условий, список результатов и план дня.
- Карточка сеанса с источником и статусом.
- Пустые состояния и экстренная пересборка при отмене сеанса.
- In-bubble HTML-виджет Telegram Bot API 10.4 (`<= 600 px` без скролла и `<input>`) и текстовый fallback.
- Виджет для внешнего партнёрского сайта.

Результат: лёгкие wireframes и единый сценарий, который затем используется в презентации.

## День 2. Техническая готовность и сквозной прототип

### 6. Подготовить инженерную базу

- Согласовать стек с учётом опыта команды.
- Создать каркас выбранной структуры проекта.
- Добавить единый запуск, `.env.example`, форматирование и базовые проверки (включая автотест размера `zlib -9 <= 4096 B` для HTML-шаблона Telegram-виджета).
- Настроить CI и защиту `main`.
- Проверить доступы к хостингу, домену, Telegram Bot API 10.4, `TypeSafe AI (Jev)` и выбранному LLM-провайдеру.

Результат: новый участник может запустить проект по README.

### 7. Проверить данные на малом вертикальном срезе

- Выбрать несколько реальных событий с открытыми источниками.
- Заполнить черновую схему данных.
- Проверить даты, часовой пояс, цену, возрастные ограничения и статусы.
- Проверить хотя бы один случай возможного дубля.

Результат: небольшой проверяемый набор данных и список проблем импорта. Объём данных не важнее их достоверности.

### 8. Собрать технический skeleton

Только минимальная цепочка:

```text
Небольшой проверенный dataset → API → один Web-запрос → один Telegram Bot API 10.4 Widget запрос
```

ИИ (`Jev` + `LLM`) подключается поверх уже работающего структурированного поиска и не блокирует его при деградации. Не строим полный продукт заранее.

### 9. Провести репетицию и заморозить план

- Пройти главный сценарий от запроса до результата.
- Зафиксировать риски и запасные варианты (обновлённые клиенты Telegram 10.4+ на всех демо-устройствах, режим `deterministic_fallback`).
- Разбить хакатонный backlog на задачи с владельцами.
- Подготовить структуру финальной презентации.

Результат: команда начинает хакатон с понятного плана, а не с выбора стека.

## Во время хакатона

Рекомендуемый порядок:

1. Сквозной MVP и развёртывание.
2. Качество данных, статусы `Occurrence` и дедупликация (`SQL veto + Jev`).
3. Web и Telegram Bot API 10.4 HTML Widgets на едином API.
4. ИИ-контур (`Jev` System 1 + `LLM` System 2), уточнения, пересборка плана и объяснимость.
5. Партнёрский веб-виджет и документация интеграции.
6. Тестирование по `evals/`, полировка, презентация.

За несколько часов до сдачи прекращаем добавлять крупные функции: только исправления критических ошибок, проверка сценария и подготовка демо.

## Критерии готовности к старту

- Все участники имеют доступ и знают свои роли.
- Полное задание и критерии оценки доступны команде.
- Исследование аналогов оформлено выводами, а не только ссылками.
- MVP и один главный сценарий демо согласованы.
- Есть схема данных и границы ответственности `Jev`, `LLM` и детерминированного ядра.
- Выбран стек, настроены запуск и CI.
- Проверены доступы к внешним сервисам и площадке развёртывания, обновлены клиенты Telegram на демо-устройствах.
- Есть приоритизированный backlog и запасной демонстрационный сценарий.

## Что сознательно откладываем

- Микросервисы без доказанной необходимости.
- Полноценная рекомендательная система с историей покупок.
- Обучение собственной модели ИИ с нуля.
- Массовый парсинг всех источников до проверки правил и качества данных.
- Платежи, личный кабинет и сложная социальная сеть, если они не требуются заданием.
