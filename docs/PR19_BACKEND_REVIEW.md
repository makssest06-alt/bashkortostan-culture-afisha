## 3. Что готово

### 3.1. Контракт и маршруты

Реализованы основные пути контракта v1:

- `GET /api/v1` — индекс API;
- `GET /api/v1/health`, `GET /api/v1/metrics`, `GET /metrics`;
- `GET /api/v1/events`, `GET /api/v1/events/:id`, `GET /api/v1/events/:id/similar`;
- `GET /api/v1/venues`, `GET /api/v1/venues/:id/schedule`;
- `GET /api/v1/cities`, `GET /api/v1/categories`, `GET /api/v1/dictionaries`, `GET /api/v1/facets`;
- `POST /api/v1/subscriptions`, `GET /api/v1/subscriptions`, `DELETE /api/v1/subscriptions/:id`;
- `POST /api/v1/feedback`.

Расширения сверх контракта:

- `POST /api/v1/assistant/query`, `POST /api/v1/assistant/confirm`;
- `GET/PATCH /api/v1/admin/events`, `GET/POST /api/v1/admin/imports`, `GET /api/v1/admin/moderation`, `POST /api/v1/admin/moderation/:id/resolve`, `GET /api/v1/admin/audit`, `GET/PATCH /api/v1/admin/applications`, `POST /api/v1/admin/reset`, `GET /api/v1/admin/traces`.

Единый формат ошибок: `{ code, message, details, request_id }`. Есть `X-Request-Id`, preflight/CORS, проверка методов, `Cache-Control`.

### 3.2. Поиск и фильтры

`backend/src/domain/search.ts`:

- фильтры: город, категория, дата/диапазон дат, цена (`price_min`, `price_max`), `free=true`, возраст, текстовый запрос, пагинация, сортировка;
- пресеты дат: `today`, `tomorrow`, `weekend`, `week`;
- `relaxations` — честно показывает, какие условия пришлось ослабить;
- `hidden_unknown_*` — не выдаёт неизвестную цену за «бесплатно», а неизвестный возраст за «0+»;
- отменённые события не показываются как актуальные;
- пагинация и `total_pages` работают.

На текущем объёме (41 событие) поиск быстрый и корректный.

### 3.3. Карточка события

- сеансы (`occurrences`), площадка, предложения (`offers`);
- `ETag`/`304` для карточек и справочников;
- `draft` → 404, `cancelled` → 200 со статусом;
- список событий отдаётся с `no-store`, карточки — с `ETag`;
- `similar` и `venues/:id/schedule` работают.

### 3.4. Справочники и facets

- `GET /cities` — 8 городов;
- `GET /categories` — 7 категорий;
- `GET /dictionaries` — объединённый справочник;
- `GET /facets` — счётчики по городам/категориям;
- `ETag`/`304` для справочников.

Для бота это источник истины: встроенный список используется только как fallback, если API недоступен или вернул пустой/битый ответ.

### 3.5. Импорт

`backend/src/domain/imports.ts`:

- JSON, CSV и `multipart/form-data`;
- нормализация и валидация строк;
- дедупликация по `source_hash` и `dedup_key`;
- слияние дублей;
- `raw_records` для трассируемости источника;
- отчёт: `added`, `updated`, `merged`, `unchanged`, `rejected` с причинами;
- повторная загрузка того же файла идемпотентна: 100/100 `unchanged`;
- лимит на размер импорта и транзакционная запись.

### 3.6. Подписки

- создание с валидацией `channel`, `user_ref`, города, категории, периода;
- список по `user_ref`;
- удаление;
- уникальный индекс от дублей;
- аудит операций.

**Чего нет:** доставки уведомлений. Подписка — это только запись фильтра; воркера, который рассылает новые события, в бэкенде нет. Это важно не путать с «подписка работает»: CRUD работает, уведомления — нет.

### 3.7. Админка

- список и карточка события, `PATCH` для правки;
- импорт CSV/JSON;
- модерация и разрешение спорных записей;
- аудит;
- заявки организаторов;
- сброс демо-данных;
- трассы ассистента.

Админка сайта сделана аккуратно: cookie `HttpOnly` + `SameSite=Strict`, проверка `Origin` для мутаций, Bearer-токен остаётся на сервере. Но у бэкенда и compose есть P0 по `ADMIN_OPEN` — см. ниже.

### 3.8. ИИ-ассистент

- без `LLM_API_KEY` работает детерминированный `rules-v2`;
- с ключом — tool-loop: до 5 вызовов инструментов за ответ;
- инструменты: `search_events`, `get_event`, `find_similar`, `get_venue_schedule`, `subscribe`, `save_feedback`;
- grounding: `grounding_ids` только по реально найденным событиям;
- защита от prompt injection: недоверенные данные карточек обёрнуты, системный промпт не раскрывается;
- подтверждение мутаций: `POST /assistant/confirm`, одноразовый токен, TTL 10 минут;
- fallback: при сбое LLM — `rules-fallback-v2`, при отключении — 503 + `Retry-After: 60`;
- трассы: `agent_traces`, маскирование `user_query_masked`, стоимость в `cost_rub`.

**Ограничения:** уровень 3 не доказан (см. §4), а расходы не ограничены (см. P0-3).

### 3.9. Инфраструктура

- PostgreSQL 16 или встроенный PGlite;
- миграции и идемпотентный seed;
- Dockerfile и корневой `docker-compose.yml`;
- healthcheck;
- Prometheus-метрики;
- структурные логи с `request_id`.

## 5. P0 — блокеры публичного стенда

> **Статус на 14.11.2026: все пять P0 исправлены в коде и покрыты тестами** (`backend/test/security.test.ts`, `backend/test/admin.test.ts`). Публичный стенд разблокирован после стандартной проверки TLS/прокси; `/metrics` закрывается `METRICS_TOKEN`; см. §10.

Это не блокеры локального демо и не блокеры мержа кода. Это блокеры **публичного** запуска.

### P0-1. Админка открыта по умолчанию

**Где:**

- `docker-compose.yml:41` — `ADMIN_OPEN: ${ADMIN_OPEN:-1}`;
- `.env.example:35` — `ADMIN_OPEN=1`;
- `web/compose.yaml:29` — `ADMIN_OPEN: ${ADMIN_OPEN:-1}`;
- `backend/src/domain/admin.ts:55` — `checkAdminAuth` пускает без токена, если `config.adminOpen`, **без проверки `NODE_ENV`**.

**Что происходит:**

- `docker compose up` без правки env поднимает API с открытой админкой;
- любой, кто достучался до `/api/v1/admin/*`, может править события, запускать импорт, читать заявки с контактами, смотреть трассы и делать `POST /admin/reset`;
- веб-админка сайта имеет более безопасный режим (`disabled` в production без токена), но compose выставляет `ADMIN_OPEN=1` и переопределяет это.

**Как чинить:**

1. Убрать `ADMIN_OPEN=1` из `.env.example` и обоих compose; по умолчанию — `0`/пусто.
2. В `checkAdminAuth` не открывать админку в production: если `ADMIN_OPEN=1` и `NODE_ENV=production` — падать на старте или отдавать 401.
3. Сделать `ADMIN_TOKEN` обязательным для production, минимум 32 случайных символа.
4. Добавить в README явное предупреждение и проверку на старте.

**Критерий готовности:** `docker compose up` без env → `/api/v1/admin/events` отдаёт 401; production с `ADMIN_OPEN=1` не стартует.

### P0-2. `TRUST_PROXY=1` и подделываемый `X-Forwarded-For`

**Где:**

- `docker-compose.yml:52` — `TRUST_PROXY: ${TRUST_PROXY:-1}`;
- `.env.example:62` — `TRUST_PROXY=1`;
- `backend/src/app.ts:127` — `getClientIp` доверяет заголовкам;
- `backend/src/domain/rate-limit.ts` — `clientIpFromHeaders` берёт **первый** адрес из `X-Forwarded-For`;
- `web/src/lib/api/forward.ts:43-44` — сайт пересылает присланный клиентом `X-Forwarded-For` как есть;
- `docker-compose.yml:35` — порт API опубликован `${API_PORT:-8000}:8000`.

**Что происходит:**

- клиент присылает `X-Forwarded-For: 1.2.3.4`, сайт передаёт его в бэк, бэк считает это адресом клиента;
- лимиты частоты (feedback, metrics, а в будущем — ассистент) обходятся сменой заголовка;
- логи и метрики получают мусорные IP;
- если порт API опубликован наружу, можно ходить в бэк напрямую, минуя сайт.

Дополнительный нюанс: при `TRUST_PROXY=0` текущий `getClientIp` возвращает `127.0.0.1` для всех, то есть лимиты становятся общими на всех клиентов. Нужен реальный socket IP, а не константа.

**Как чинить:**

1. По умолчанию `TRUST_PROXY=0`.
2. В production доверять только известному прокси: фиксированное число хопов или CIDR, а не любому заголовку.
3. На сайте **перезаписывать** `X-Forwarded-For` адресом сокета/прокси, а не пробрасывать клиентский.
4. Не публиковать порт API наружу: только внутренняя сеть compose, сайт — единственная точка входа. Если нужен прямой доступ — bind на `127.0.0.1` и отдельный reverse proxy.
5. При `TRUST_PROXY=0` брать реальный адрес соединения.

**Критерий готовности:** запрос с поддельным `X-Forwarded-For` не меняет ключ лимита; прямой запрос на порт API снаружи невозможен; в логах реальные IP.

### P0-3. У ассистента нет rate-limit и бюджета

**Где:**

- `backend/src/app.ts:656` — `POST /assistant/query`;
- `backend/src/app.ts:695` — `POST /assistant/confirm`;
- `backend/src/domain/assistant/index.ts` — `rateLimiter` прокидывается, но используется только инструментом `save_feedback`;
- `backend/src/domain/assistant/llm.ts` — таймаут 12 с, до 5 tool-calls, но **нет** лимита запросов, токенов и дневного бюджета.

**Что происходит:**

- каждый запрос может стоить денег: один или несколько LLM-раундов, до 5 tool-calls;
- цикл запросов одним клиентом выжигает ключ и бюджет;
- `confirm` тоже без лимита;
- при публичном стенде это прямой cost-DoS.

**Как чинить:**

1. Слайдящий лимит на `query` и `confirm` по IP и/или `user_ref` (например, 5/10 мин и 30/сутки).
2. Ограничение `max_tokens` на запрос и на ответ.
3. Дневной/месячный бюджет с автоматическим отключением LLM и переходом на `rules-v2`.
4. `429` + `Retry-After`, метрика отказов, алерт при 80% бюджета.
5. Отдельный лимит на `confirm`, чтобы нельзя было перебирать токены.

**Критерий готовности:** N+1 запрос → 429; при превышении бюджета ассистент отвечает управляемо (503/429 или rules-fallback), а не молча тратит деньги.

### P0-4. Confirmation-токены не привязаны к пользователю

**Где:**

- `backend/src/domain/assistant/tools.ts:679` — токен `cnf_` + 6 случайных байт (48 бит);
- `backend/src/domain/assistant/tools.ts:796` — `confirmPendingAction`;
- `backend/src/domain/assistant/tools.ts:877` — `userRef: row.user_ref ?? ctx.userRef`.

**Что происходит:**

- подтверждение ищется только по `confirmation_id`;
- `user_ref` из запроса не сверяется с `row.user_ref`;
- любой, кто получил токен, может подтвердить подписку или заявку, созданную для другого `user_ref`;
- TTL 10 минут, токен одноразовый — это хорошо, но 48 бит энтропии и отсутствие привязки к сессии/пользователю — плохо;
- токен хранится в БД в открытом виде.

**Как чинить:**

1. Генерировать минимум 16 байт (128 бит).
2. Хранить хеш токена, а не сам токен.
3. При подтверждении сверять `user_ref`/сессию и отдавать 403/404 при несовпадении.
4. Ограничить TTL (5 минут достаточно) и добавить rate-limit на `confirm`.
5. Писать в аудит, кто подтвердил и что именно.

**Критерий готовности:** подтверждение с чужим `user_ref` → 403/404; токен нельзя использовать повторно; энтропия ≥ 128 бит.

### P0-5. Удаление подписки без `user_ref`

**Где:**

- `backend/src/domain/subscriptions.ts:222-223` — если `user_ref` не передан, удаление идёт только по UUID;
- `backend/src/app.ts:607` — `GET /subscriptions?user_ref=...`;
- `backend/src/app.ts:615` — `DELETE /subscriptions/:id?user_ref=...`.

**Что происходит:**

- любой, кто знает UUID подписки, может её удалить без `user_ref`;
- `user_ref` используется как bearer-секрет в query string: он попадает в логи прокси и мониторинга, а при открытии URL напрямую — в историю браузера;
- `GET /subscriptions` возвращает `user_ref` в теле;
- rate-limit на подписки нет, можно спамить созданием.

**Как чинить:**

1. Сделать `user_ref` обязательным для `DELETE`; без него — 400/401.
2. Не принимать `user_ref` в query string: только заголовок `Authorization`/подписанный токен.
3. Не возвращать `user_ref` в списке (или возвращать только маску).
4. Добавить rate-limit на создание/удаление.
5. Проверить, не логируется ли query string целиком.

**Критерий готовности:** `DELETE` без `user_ref` → 400/401; с чужим `user_ref` → 404; `user_ref` не виден в логах и URL.

## 8. Как сайт работает с бэкендом

### 8.1. Два режима

**Режим моков:** `NEXT_PUBLIC_API_BASE_URL` пуст. Сайт берёт данные из `web/src/data`, `db.ts`, `search.ts`. Бэкенд не нужен.

**Режим бэкенда:** `NEXT_PUBLIC_API_BASE_URL` задан. Сайт ходит в API.

### 8.2. Схема

```text
                         ┌─────────────────────────────┐
                         │  Браузер / виджет на сайте  │
                         └──────────────┬──────────────┘
                                        │ same-origin /api/v1/*
                                        ▼
                         ┌─────────────────────────────┐
                         │  Next.js: route handlers    │
                         │  web/src/app/api/v1/*       │
                         │  forwardToBackend()         │
                         └──────────────┬──────────────┘
                                        │ HTTP + X-Forwarded-For
                                        ▼
┌──────────────────┐        ┌─────────────────────────────┐
│ Server Components│───────▶│  Backend API (Hono)         │
│ server.ts        │ direct │  /api/v1/*                  │
│ 8s / 20s timeout │        │  admin / assistant          │
└──────────────────┘        └──────────────┬──────────────┘
                                           │
                                           ▼
                                  PostgreSQL 16 / PGlite
```

### 8.3. Что куда ходит

| Поток | Путь | Особенности |
|---|---|---|
| Браузер, виджет, `curl` со страницы `/developers` | сайт `/api/v1/*` → `forwardToBackend` → API | Сайт — единая точка входа; CORS сайта; таймаут 15 с |
| Серверные компоненты, `generateMetadata` | `web/src/lib/api/server.ts` → API напрямую | Таймаут 8 с, ассистент — 20 с; API должен быть доступен из контейнера сайта |
| Ассистент из браузера | сайт `/api/v1/assistant/query` → API | Таймаут 25 с; при 503 сайт показывает обычный поиск |
| Админка | браузер → сайт `/api/v1/admin/*` → API | Cookie `HttpOnly` + `SameSite=Strict`, проверка `Origin`, Bearer-токен остаётся на сервере |
| `/metrics` | не проксируется общим `[...path]` | Входит в `NOT_FORWARDED` вместе с `admin`; сайт наружу его не отдаёт |

### 8.4. Где проходит граница доверия

- Публичный вход — сайт. API должен быть внутренним.
- Сайт пересылает `X-Forwarded-For` — это одновременно нужно для лимитов и опасно (P0-2).
- Админка сайта защищена лучше, чем API: cookie + Origin + серверный токен. Но `ADMIN_OPEN=1` в compose ломает и её.
- Если открыть порт API наружу, все P0 становятся доступны напрямую, без сайта.
